# SECURITY.md

Internal engineering reference **and** pentest/audit prep document for GetSetPaid. Consolidates security decisions already made across `CLAUDE.md` and the PRD (`getsetpaid_crm_prd.docx` §10, §18) into one place, plus defines rate limits, incident response and vulnerability disclosure that didn't exist anywhere yet.

This is not the public-facing Trust Centre page (PRD §12) — it is written for engineers and external security testers, not customers. Nothing here is a substitute for the pre-launch independent penetration test (PRD §10.8) or legal/privacy counsel review (see `CLAUDE.md` § Legal and regulatory compliance).

## 1. Principles

- No feature is production-ready until threat modelling, access-control tests and OWASP-aligned tests pass — security is an acceptance criterion, not hardening applied after the fact.
- Least privilege everywhere: roles, database roles, service accounts, superuser access.
- Private by default: tenant data never crosses into the network/public surface without an explicit, tested, opt-in policy.

## 2. Tenancy and Row Level Security

- RLS is enabled on every tenant-owned table before the application can reach it. Separate policies per operation (SELECT/INSERT/UPDATE/DELETE) where useful.
- Access is derived from the authenticated session and organisation membership, checked **in the database** — never from a client-supplied organisation ID.
- **Network tables, as built (Phase 6) — the base table is deliberately readable and the VIEW is the masking control, not the policy.** `network_profiles_select_published_directory` (`20260904003000`) is **the one policy in the whole schema that permits a cross-tenant read**, and its own comment says why: a row policy filters rows, it cannot filter columns, so a caller who queried `public.network_profiles` directly would see `organisation_id`, `entity_id` and every value column, including ones the publisher marked `hidden`. **Two views are the only sanctioned read path into another organisation's published data**: `public.network_directory` (`network`-level fields only) and `public.network_connected_profiles` (`network` + `connections`-level fields, for an organisation on either side of an accepted `network_connection_requests` row — Q80's org-to-org symmetry). **An accepted row can only be made by the recipient's UPDATE**: since `20261017000000` a request is born `pending` — a `BEFORE INSERT` trigger (`private.connection_request_born_pending`, binding every non-owner role including `service_role`) refuses any other status or a pre-filled response with 23514 and stamps `requested_by`/`requested_at` from the session and the clock, and the INSERT policy's WITH CHECK carries the same status terms. Until then a sender could INSERT a row already `accepted` and read the target's `connections`-level fields without consent (pre-existing since Phase 6, measured, Task 9b review C1). **And the UPDATE cannot forge one either** (since `20261020000000`, Task 9b re-review N1): a `BEFORE UPDATE` trigger (`private.connection_request_bound_update`, same owner-role exemption) refuses with 23514 any change to the four organisation/profile columns, `requested_by`, `requested_at` or `created_at`; binds `accepted`/`declined` to a `manage_network_connections` holder in the STORED recipient organisation that publishes, and `withdrawn` to one in the stored sender organisation; and stamps `responded_at`/`responded_by` from the clock and the session (a same-status edit of either is refused). `authenticated` holds UPDATE on `(status, responded_at, responded_by)` only, so a PATCH naming a party column is a 42501. Until then the two permissive UPDATE policies, ORed clause by clause, let a sender rewrite its own pending row into `X -> sender accepted` and read X's `connections`-level fields, with a back-dated `responded_at` keeping X's email silent (pre-existing since Phase 6, measured, `rls_phase6_network.sql` § NQ). Both carry `security_invoker = true`, so row reachability is still the caller's own `network_profiles` policy above — one gate, not two that can drift — and both are structurally pinned to a fixed dependency set (**the N2 invariant**): `network_directory` to exactly `{public.network_profiles}`, `network_connected_profiles` to exactly `{public.network_profiles, public.network_connection_requests}`, nothing else, ever. Asserted from `pg_depend`, not promised in a comment, by `supabase/tests/rls_phase6_network.sql` § ND, with a non-vacuity control (`public.event_finance_summary` must independently resolve to `{financial_entries}`, proving the query can see dependencies at all) — the failure mode this catches is a future edit joining a private table into either view to resolve a nicer display name. A field the publisher marks `hidden` is additionally stored as **NULL** in the base column (`network_profiles_hidden_fields_are_null`, N3), so the view's mask is the second of two controls, not the only one. Application code must never select from `public.network_profiles` for a foreign organisation — `lib/network/discovery-list.ts` and `lib/network/discovery.ts` name the two views as their only tables, and `tests/unit/network/no-private-table-in-network-path.test.ts` is the source-only, CI-visible census that a future edit cannot grow a shortcut around them invisibly. `network_links` carries only ordinary tenant-scoped policies — no cross-tenant SELECT at all (Q82: "the profile's owner is never told" who linked it). `network_connection_requests` is narrower than "tenant-scoped" but not zero: `network_connection_requests_select_view_network` is a disjunction over `from_organisation_id` OR `to_organisation_id`, so **either party to a request reads that request's row** — a recipient organisation reads a row another tenant inserted, learning that tenant's `from_organisation_id` and `from_network_profile_id`. That is the point of a two-party record (the recipient must see who is asking, Q78), and it is the table `network_connected_profiles` resolves the accept unlock against — a tester should look at it, not be told there is nothing there. So `network_profiles_select_published_directory` is the only *unilateral* cross-tenant read among the three tables — the only policy through which an organisation reads another tenant's row without being a named party to it — and it is written so that fact "is impossible to miss" (its own comment, verbatim). Regression tests: `supabase/tests/rls_phase6_network.sql` (§ ND the dependency assertion, § NG the `anon`-grant census across all five objects — three tables, two views) and `supabase/tests/network_leakage_phase6.sql` (the consolidated adversarial proof, every tenant-private table, query path by query path). See § 10's "Network privacy leakage" row for the residuals this does not close.
- Finance and audit tables carry additional, more restrictive policies than general CRM data. **`public.financial_entries` (Phase 5) is the most restricted surface in the product, and the shape is deliberate.** It has **three** policies and no fourth: SELECT, INSERT, UPDATE, and **no DELETE grant at all** — a financial record is soft-deleted (7-year retention, § 8) and never hard-deleted, so the DELETE policy that does not exist is the control. Two new permission keys carry it, `view_finance` and `manage_finance` (`20260903002000`), held by Owner, Admin and Finance only; `role_requires_mfa('finance')` was already true, so both keys are simply not held below `aal2` and the MFA gate needed no new code. **Reads are NOT entitlement-gated and that is a decision, not an omission** (founder Q67): the SELECT policy names `private.permitted_organisations('view_finance')` and nothing else — no `finance_module` term — so an organisation that downgrades from Pro keeps reading its own finance history, matching "downgrading must never silently delete data" (`CLAUDE.md` § Permissions). The **write** policies additionally name `private.finance_module_organisations()` (Pro only), and the tier conjunct sits in `WITH CHECK` only, deliberately **not** in the UPDATE's `USING`, so a downgraded write refuses with a loud `42501` rather than PostgREST's `204`, which is indistinguishable from success. The same split reaches the finance **custom-field value** path: `private.entity_is_manageable`'s `financial_entry` arm carries the `finance_module` term (`20260903030000`) and `entity_is_visible`'s does not. `public.event_finance_summary` is a `security_invoker` **view**, so its base read runs under the caller's own SELECT policy rather than the view owner's — a caller without `view_finance` gets no row, not a zeroed one. Regression tests: `supabase/tests/rls_phase5_finance.sql` (§ FB shape, § FD the six non-finance roles, § FE the tier gate, § FF the aal1/aal2 inversion, § FI the custom-field value path including the downgrade case) and the "Phase 5 finance at the API surface" HTTP block, which elevates a real session with a real TOTP enrolment.
- **Break-glass impersonation, as built (Phase 7 Task 2) — the ONE place a non-member reads a tenant, and the grant is derived, not minted.** `CLAUDE.md` § Superuser dashboard makes this the only sanctioned deep-access path in the product ("No direct tenant-data access outside impersonation"), so its shape matters more than any other single control. `public.impersonation_sessions` (`20260908020000`) has **two SELECT policies and no write policy of any kind**, and `authenticated` holds `SELECT` on it and nothing else — every transition goes through one of five `SECURITY DEFINER` RPCs (`request_impersonation`, `accept_impersonation_request`, `decline_impersonation_request`, `start_impersonation_session`, `end_impersonation_session`), each carrying its own authorisation guard **and its own audit write in the same transaction**. **No synthetic membership row is ever created**: the grant is `private.impersonated_organisations(permission)`, which returns the target organisation only while (a) a row for this caller is `status = 'active'`, (b) `expires_at > now()` — evaluated on **every** permission check, so expiry is immediate and needs no sweep job, (c) the caller still passes `private.has_platform_permission()` (still allowlisted, still `aal2` — de-allowlisting or dropping to `aal1` kills a live session with no row to update), and (d) the permission is one `public.role_permissions` grants the **`read_only`** role, joined rather than hardcoded so the envelope cannot drift from the product's own definition of Read Only (Q96). - **Billing/feature override tables, as built (Phase 7 Task 4) — RPC-only writes, one deliberately cross-tenant read, and reason columns every member of the target org can read.** `public.organisation_billing_overrides` and `public.organisation_feature_overrides` (`20260909000000`) are writable by no client role except through the four audited RPCs (`grant_billing_override` / `revoke_billing_override` / `grant_feature_override` / `revoke_feature_override`, `SECURITY INVOKER` so the policies are the enforcement, with `private.log_override_event()` as the `SECURITY DEFINER` audit bridge): the INSERT/UPDATE policies require `private.has_platform_permission()` **and** a transaction-scoped marker (`private.override_transition_in_progress()`, its own GUC `app.override_transition`) that only the RPCs set — so a raw PostgREST POST/PATCH from the superuser's own browser matches nothing — and a policy-independent `BEFORE INSERT OR UPDATE` trigger (`private.override_table_guard()`) refuses the same writes without consulting any policy. Regression tests: `supabase/tests/rls_phase7_overrides.sql` (56 assertions — grant/expiry/revoke both sides of the boundary, RPC-only writes attacked as the org's own Owner and as the superuser's raw PATCH, foreign-admin-reads-zero, downgrade-deletes-nothing, audit trail) and `tests/integration/entitlements/billing-override-matches-db.test.ts` (the TypeScript↔SQL binding, including seats-only + cancelled).

### The export reads as the requester (Phase 8 Task 4)

A data export is the densest read in the product: one archive is every
tenant-owned table of a workspace, or everything the platform holds about one
person. The question that decides whether it is safe is **whose access rights
build it**, and the answer is *the requester's*, enforced by the same policies
their browser meets rather than by a second copy of the rules.

`public.export_read_page()` runs the read through
`private.export_read_page_as_requester()`, a `SECURITY DEFINER` function owned
by a purpose-made role, **`export_reader`**. Three properties make RLS apply
inside it, and all three are load-bearing:

1. `export_reader` owns no table, so RLS is never skipped for it as an owner;
2. it has no `BYPASSRLS` and cannot log in;
3. it is a MEMBER of `authenticated`, and every policy in this schema is
   written `to authenticated` — a policy applies to any role that
   `pg_has_role(..., 'MEMBER')` of the one it names.

The caller installs the requester's claims in `request.jwt.claims` **from the
job row** — `sub` is `export_jobs.requested_by` and `aal` is
`export_jobs.requested_aal`, both stamped at insert by the trigger and
immutable afterwards — so neither the subject nor the assurance level is the
runner's to choose, and a replay cannot promote an `aal1` request to `aal2`.
The claims are restored after the read.

The consequence worth stating: **an Owner's workspace export contains no other
member's `private` notes**, because `notes_select_by_visibility` decides it,
not this code. Measured both ways in `supabase/tests/rls_phase8_exports.sql`
§ XP and in `tests/integration/export/runner.test.ts`, each of which asserts
the requester's OWN private note is PRESENT before asserting a colleague's is
absent — an engine that returned nothing would otherwise pass the security
assertion perfectly, and the first cut of this mechanism did exactly that
(Postgres refuses `SET role` inside a `SECURITY DEFINER` caller; the positive
control is what caught it).

**Four account-export tables are the exception, and each is an exception for
a stated reason.** `audit_events` and `feedback` are superuser-only by policy,
`platform_admins` has no SELECT policy at all, and `impersonation_sessions` is
reachable only through a permission in a workspace the person may have left —
so a requester-RLS read of any of them would have returned zero rows and
passed. They are read as the definer, each filtered to the catalogue's scope
column and PROJECTED to named columns (`audit_events` without

## 3. Input handling

- All queries are parameterised or built with a trusted query builder — no string-concatenated SQL, anywhere.
- Search/filter/sort inputs map to an allowlist of column names and operators; free-form input never becomes a column/operator name.
- Rich text is sanitised against stored and reflected XSS. URLs are validated against an allowlist of protocols (`javascript:` and `data:` rejected). `dangerouslySetInnerHTML` is avoided; where unavoidable, it requires security review.
- A strong Content Security Policy is shipped with the Next.js app.
- **Legal documents (Phase 8 Task 1) are the one place a platform operator's free text becomes a public page, and it never becomes HTML.** The stored body is a small Markdown subset (`##`/`###` headings, `-`/`1.` lists, `**bold**`, `[text](target)`, three `{{placeholders}}`) that `lib/legal/markup.ts` parses into typed blocks and `components/legal/legal-body.tsx` maps to React elements — there is no HTML string on the path and no `dangerouslySetInnerHTML` under `components/legal`, `lib/legal`, `app/legal` or the editor (asserted from source). Three layers refuse the same things: **save time** (`validateDraft` names the problem beside the field), **the database** (CHECK constraints: a link target must start `https://`, `mailto:` or a single `/`; no `<` followed by a letter, `/` or `!`; no unknown placeholder; the Cookie Policy, Subprocessors, Contact and Vulnerability Disclosure pages must keep their generated placeholder; and, since fix round 1, a placeholder only where it renders — `legal_documents_body_placeholders_placed` carries `lib/legal/markup.ts`'s five `PLACEMENT_PATTERNS` verbatim, proved equal to the parser's linear scan over a generated corpus against the LIVE constraint), and **render time** (a refused link renders as its text only, a tag is stripped, and React escapes the rest). `javascript:`, `data:`, `vbscript:`, `http:`, scheme-relative `//host` and targets containing whitespace or control characters are refused in every case variant (`tests/unit/legal/markup.test.ts`, `renderer.test.tsx`). **A scheme is accepted in lower case only** (fix round 1, M4): the parser used to accept `HTTPS://` and `MAILTO:`, which the case-sensitive CHECK refuses, so the layers disagreed; the stricter rule won. **The parse is linear** (M5): the original alternation regex took 5.8 s on a 100 000-character body of `[`, on every anonymous page view; a single scan replaced it and a timing test at the length limit fails the old form. **Fix round 1 left four quadratic expressions on the same path** (fix round 2): the per-line `/\s+$/` trim (4 to 6 s on a 100 000-character whitespace run), the heading, bullet and numbered-list patterns (quadratic when a U+2028 follows a long whitespace run, since `\s` matches it and `.` does not), and the `mailto:` address pattern (quadratic on a run of dots, and the database accepts any target beginning `mailto:`); plus the save-time placement check's `/[ \t]+$/` trim. Each is now a linear helper in `lib/legal/markup.ts`, proved equal to the regex it replaced on a generated corpus, and the timing test fails each old form when it is restored. The contact-address regex in `lib/legal/contact.ts` was checked and measured linear (under 1 ms at 100 000 characters). Mutation-tested: making the link check accept everything reds 27 unit assertions; disabling tag stripping reds 8 — and leaves the `<script>`/`<iframe>` render checks green, because React's escaping is the real control and stripping is defence in depth.


**`public.events.ticket_link` is guarded three times, and the middle one is stronger than its own comment claims (measured, Phase 3 Task 8).** `normaliseWebsite()` refuses a non-http(s) scheme on the way in, `safeHref()` refuses it on the way out (a value it rejects renders as inert text, never as an anchor), and the column additionally carries `events_ticket_link_is_http`, `check (ticket_link is null or ticket_link ~* '^https?://')`. That CHECK's own comment (`supabase/migrations/20260901000000_events_and_lineup.sql:147`) calls itself "DEFENCE IN DEPTH, NOT THE CONTROL"; the phrase "a row written before it, by an import, or by a direct PostgREST PATCH is still possible" is the DETAIL PAGE's comment (`app/(app)/[orgSlug]/events/[eventId]/page.tsx:60-64`), not the constraint's — and on this column none of the three is possible today: it is a **validated** CHECK (not `NOT VALID`), so it binds every writer including `postgres` and `supabase_admin`, and `public.events` was created *with* it, so there are no older rows. Phase 3 Task 8 tried to plant a `javascript:` ticket link as `postgres` for a render test and could not. **Two things follow.** A pentester should not spend time hunting for a stored `javascript:` on this column — but `contacts.website` and `contacts.socials` have **no** equivalent CHECK and a hostile value *is* plantable there, which is why `tests/e2e/tenant-breakout.spec.ts` plants one and asserts the render. And nobody should weaken `safeHref()` on the strength of the CHECK: it is one column's constraint, it does not run on render, and it does not normalise.

## 4. Authentication and session security

- Identity: Supabase Auth. Email/password and magic-link/OTP at MVP; **Google SSO ships at MVP**, Microsoft SSO is post-MVP.
- Session limits: **30-minute inactivity timeout, 12-hour absolute session lifetime.**
- MFA is **required** for Platform Superuser, Organisation Owner, Admin and Finance roles. Optional (not enforced) for all other roles at MVP.
- MFA is **enforced at every sign-in, not just at enrollment**. A privileged user with a verified TOTP factor who signs in at `aal1` is challenged for a code before reaching the app — an enrolled-but-never-challenged factor satisfies the requirement in name only. Founder decision, 2026-08-27.
- **MFA recovery (lost authenticator) has no self-service path at MVP.** Because the challenge is enforced, a privileged user who loses their TOTP device cannot sign in at all. There are no backup codes and no admin reset UI. The only recovery today is a manual operator action: delete that user's row from `auth.mfa_factors` in the Supabase dashboard (SQL editor, filtered by `user_id`) after verifying the requester out-of-band, which drops them back to the enrollment gate on next sign-in. **This is a deliberate MVP gap, not an oversight** — self-service recovery (backup codes at enrollment, plus a superuser-initiated, audited reset) belongs to Phase 7 (Admin/Security) alongside the rest of the superuser dashboard. Until then: the manual deletion must be treated as a high-risk admin action — verify identity out-of-band before performing it, since it is a complete bypass of the second factor.
- **MFA is enforced in the database, not only in the UI.** `public.has_permission()` and `private.has_platform_permission()` return false for an MFA-required role on a session that has not reached `aal2` (`supabase/migrations/20260827210000_mfa_aal_permission_gate.sql`), so every write policy in the schema inherits the requirement. The app-layer gate (`lib/auth/mfa-gate.ts`, plus `assertMfaSatisfied()` on the privileged Server Actions) gives a readable refusal and stops side effects outside the database; it is not the enforcement. The anon key ships in the browser bundle by design, so anyone holding a session token can call PostgREST directly and bypass the entire Next.js app — the database is the only chokepoint on that path.

- Integration audit attribution (the tombstone actor on server-side rows) is described in section 7.

### Known limitation: MFA gates privileged WRITES, and — since Phase 2 — CRM READS

**Narrowed on 2026-08-28 (Phase 2, Task 2). The CRM tables are now `aal2`-gated for reads as well; Foundation's tables are not.** Read the whole section: the half that remains open is still the half a pentester will find.

**What changed.** Every Phase 2 CRM policy — all twelve tables, reads included — is built on `private.permitted_organisations()`, which restates `public.has_permission()`'s body including the `aal2` clause. So an Owner, Admin or Finance user on an `aal1` session now reads **zero** contacts, companies, agencies, artists, venues, rooms, links, representations, fee history, custom field definitions, custom field values and merge records. Measured over real HTTP with a real password-grant token plus the public anon key, i.e. the exact stolen-password request this section is about (`supabase/tests/run-rls-tests.sh`, "Phase 2 CRM at the API surface"), and in psql (`rls_phase2_crm.sql` § J).

**Why that is not the lockout described below.** The enrolment path needs `profiles`, `organisations` and `organisation_memberships`. It needs no CRM row. So an un-enrolled Owner still signs in, still loads the app, still reaches the enrolment screen — asserted as a lockout guard at both layers — and simply sees an empty CRM until they present a factor.

**What is still open.** A stolen `standard_user`, `booker`, `manager`, `venue_manager` or `marketing` password still reads that user's CRM rows at `aal1`, because MFA is **optional** for those roles at MVP and there is no factor to present. And Foundation's own read policies are unchanged, for the reason in the next paragraph. So the section title's original claim still holds for most of the product; it no longer holds for the largest tenant-data surface in it.

**"MFA gates CRM reads" reads stronger than it is, so state the residue explicitly.** A stolen `aal1` Owner password still yields **the organisation's entire user directory** — measured over HTTP: `profiles?select=*` returns 200 with every colleague's name and email, `organisation_memberships` returns 200 with the full role map, and only the CRM tables return zero rows. That is the enrolment-path exemption working as designed, not a second defect, but it is what an attacker actually gets and it should not be discovered during a pentest.

**Verified end to end, not assumed.** With a real TOTP factor rather than a hand-made claim set: an `aal1` password session reads `profiles`/`organisations`/`organisation_memberships`, `POST /auth/v1/factors` enrols, challenge-and-verify moves the same session to `aal2`, the CRM then reads and writes normally — and the *original* `aal1` token still returns zero rows on every CRM table. **The one thing Tasks 3-7 must not do is put a CRM query into the app shell, the MFA gate components, or `lib/auth`.** The moment a CRM read appears above `MfaEnrollGate` in `app/(app)/layout.tsx`, the un-enrolled privileged user stops being able to reach the enrolment screen and this stops being safe.

**A stolen password for a role where MFA is optional yields read access to that user's data at `aal1`.** This is a deliberate, understood boundary rather than an open defect, and it is written down here so it is found by review rather than rediscovered by a pentester.

The `aal2` requirement is attached to *permissions*, so it bites on writes. It is deliberately **not** attached to Foundation's read policies — `organisation_memberships_select_own` / `_select_same_organisation`, `profiles_select_own` / `_select_shared_organisation` and `organisations_select_member` all resolve to `auth.uid()` or `private.is_active_member()` and never call `has_permission()`. That is not an oversight: **gating those reads is precisely the lockout that would stop an un-enrolled user reaching the enrolment screen at all.** A privileged user who has never enrolled has to be able to load the app far enough to enrol, and there is no other way in. The CRM tables escape that argument only because nothing on the enrolment path reads them.

Two `SECURITY DEFINER` functions are also outside the gate, because they must be. Both are PostgREST-routable, and for both the MFA guard is app-layer only:

- `public.create_organisation()` — measured: an `aal1` session gets `200`. It cannot consult `has_permission()`, because a brand-new user holds no membership anywhere and the organisation they are creating is what makes them an Owner.
- `public.accept_invite()` — measured: a stolen-password admin invitee at `aal1` gets `204` and the membership becomes an active admin.

**Why this is not privilege escalation.** That newly-active admin's `has_permission()` is still `false` at `aal1`, so no privileged write is reachable: they cannot invite, cannot change roles, cannot rename or soft-delete the org, cannot touch entitlements or read the audit log. What the attacker gains is **read access to that org's CRM data**, which is exactly what a stolen password already granted before MFA existed.

**Why closing it is not straightforward.** Any fix has to distinguish "a session that has not presented a factor because it is on its way to enrol" from "a session that has not presented a factor because it never will", and those are the same session until the user acts. Candidate approaches, none free:

- Gate reads on `aal2` **except** the narrow set the enrolment screen needs. Workable, but the allowlist becomes a security-critical dependency of the UI: any new query on the enrolment path silently locks every privileged user out, invisibly to build, lint and type-check.
- Redirect rather than content-swap in `app/(app)/layout.tsx`. Improves the app path only and does nothing for a direct PostgREST call, which is the path that matters.
- Force the MFA challenge at the GoTrue level so no `aal1` session is ever issued to a privileged user. The cleanest answer, and not available: assurance level is per-session and Supabase issues `aal1` on password sign-in regardless of enrolled factors (measured, `tests/integration/mfa/mfa-lifecycle.test.ts`).

**Updated 2026-09-08 (Phase 7 Task 1) — the surface this paragraph forecast has now landed, and the trade-off did NOT change.** The audit log viewer (`/super/audit-log`, `lib/admin/audit-log.ts`) is the first genuinely read-sensitive cross-tenant surface in the product, and it reads `public.audit_events` through the SAME policy this whole section is about (`audit_events_select_platform_superuser`, gated on `has_platform_permission('view_audit_log')`) -- which was `aal2`-gated from the moment it shipped in Foundation, unlike the Foundation reads (`profiles`/`organisations`/`organisation_memberships`) this section's open gap actually concerns. So an `aal1` stolen-superuser-password session gets **zero** audit rows, not a widened version of the gap above: `tests/integration/rls/rls.test.ts` section D already measured this before Phase 7 existed, and the new self-audit RPC (`public.audit_superuser_audit_log_view`, section H of the same file) checks the identical `aal2` predicate before it writes anything. The forecast in this paragraph was that a read-sensitive surface landing would change the CALCULUS for whether to close the Foundation-reads gap (make the cost of leaving it open higher); having actually built one, the honest update is that it did not, because the new surface was never part of the gap in the first place -- it is aal2-gated by construction, same as every other platform-permission-gated policy since `20260827210000_mfa_aal_permission_gate.sql`. The Foundation-reads gap itself is UNCHANGED and still open; the compensating controls are still the ones in this section: the 30-minute inactivity timeout, the 12-hour session timebox, and the fact that every privileged *write* is refused. Impersonation (Phase 7 Task 2, not yet built) is the surface that could still genuinely change this calculus, since a break-glass session acting AS another organisation is a different shape of risk than a read gated the same way every other platform permission already is.

- Step-up re-authentication (re-enter credentials/MFA) is required before: changing security settings (MFA, password, email), large data exports, deleting organisation data, and any high-risk admin/superuser function — including impersonation.
- Step-up prefers MFA re-verification over password re-entry: a password re-entry returns an `aal1` session (downgrading an MFA user) and mints a new session row (restarting the 12-hour absolute clock), so it is used only where no verified factor exists. A user with neither a verified factor nor a password identity (Google SSO only, no MFA) currently cannot satisfy step-up at all and is failed closed — closing that properly needs GoTrue's `reauthenticate()` email-nonce flow, tracked for Phase 7.
- **STEP-UP IS AN APPLICATION-LAYER CONTROL, EVERYWHERE IT EXISTS, AND A PENTESTER WILL FIND THE POSTGREST PATH.** Recorded here rather than left implied (Phase 8 Task 4 review, finding M6), because the bullet above states step-up as a property of the ACTION and it is a property of the app's route to that action. `checkStepUp()` reads "was a credential presented in the last five minutes" out of the session's AAL timestamps, which is a fact about a JWT that no database rule can see, so no policy, trigger or CHECK anywhere in this schema carries a step-up term. **Every step-up gate in the product has this shape** — publishing a legal version and recording counsel's review, the three organisation-lifecycle RPCs, the four override RPCs, requesting and starting an impersonation session, rejecting a data subject request, and (Phase 8 Task 4) starting a WORKSPACE export. Where the write path is a `SECURITY DEFINER` RPC granted to `authenticated`, calling that RPC straight over PostgREST skips step-up and nothing else; where the write path is a table with a client `INSERT` grant — `public.export_jobs` is the one in Task 4 — a scripted `POST /rest/v1/export_jobs` with an Owner's access token creates the job without it.
  **What the database still enforces on that path, measured rather than assumed:** `private.export_jobs_before_insert()` stamps `requested_by` from `auth.uid()` (the column is outside the grant, so an insert naming it is 42501) and `requested_aal` from the session honestly, `private.permitted_organisations('export_organisation_data')` applies the role's own MFA requirement, and the archive is therefore built under a real, permitted, aal2 Owner's rights and downloadable by that person alone. So the residual is exactly "a privileged action that should have asked for a fresh credential did not", not a privilege escalation and not a wider archive.
  **It is consistent rather than special**, which is why the answer is a note and not a redesign: closing it for one feature would mean minting a short-lived, single-use server token for every step-up action and checking it in the database, which is a real mechanism and belongs to whichever phase closes it for ALL of them at once. Until then, step-up is a control against a borrowed BROWSER, not against a stolen access token — and a stolen access token is already inside every other gate in this list.
- Active-session listing with remote revocation is available to every user.
- Superuser impersonation is break-glass only: the superuser requests it, the target org's admin must accept, the session is time-boxed, and the whole flow is audited (actor, org, reason, start/end). No silent or unilateral impersonation.
- **Superuser dashboard** (single hardcoded superuser account at MVP): never exposes tenant record content directly — only aggregate metadata (seat count, storage, record counts). - Every unbounded list/API endpoint is paginated (cursor/keyset for activity feeds); server-side page-size ceilings, never a client-defined unlimited limit.
- Exports are async and bounded — no synchronous unbounded export endpoint. **True as built since Phase 8 Task 4, and here is what each half means.** *Async*: a request writes a `public.export_jobs` row and returns; the archive is built outside that request, by `lib/export/runner.ts`, reached two ways — the request nudges it through `after()` once its response has been sent (the latency), and `pg_cron` calls `POST /api/exports/run` on the same ten-minute tick as the incident digest (the retry, for a job whose nudge died with its process). *Bounded*: `private.export_limits()` is the one declared place, with a page size (500, keyset, never OFFSET), a per-table row ceiling, a whole-job row ceiling and a 40 MiB archive ceiling, plus one live job per subject as a partial unique index. **A job that would exceed a ceiling FAILS with a recorded reason and never truncates** — a truncated statutory access response is a wrong answer given with confidence.

**The Connection-requests row is new, and org-scoped on purpose.** Founder ruling Q79 (2026-09-07) made a declined connection request re-requestable, which removed the one zero-cost anti-harassment control in a product with no blocking, muting or moderation; `FOLLOW-UPS.md`'s own Q79 entry names this limiter as the mitigation. Metering the DIRECTORY does not cover it — that bounds how fast an abuser can FIND organisations, not how fast they can pester ones they already found, and a request is a server action that never passes the list chokepoint. The budget binds the **organisation**, not the user: a per-user budget is bypassed by inviting a colleague (six roles hold `manage_network_connections`), and the pestered workspace experiences one workspace regardless of whose account clicked. The crossing files a `rate_limit_tripped` alert, which is the first time network harassment is visible to anyone at all. **The number was a recommended default and is now a founder ruling** (Q112, CONFIRMED AS SHIPPED 2026-09-15) — changing it is still one UPDATE to `rate_limit_policies` and one line here, no code.

**And it is enforced at the WRITE, not in the application, because the application-only version was bypassable.** As first shipped the only meter was a `consumeRateLimit()` call inside `sendConnectionRequestAction`, while `public.network_connection_requests` carries an `INSERT` grant for `authenticated` and a permissive `INSERT` policy — so a user who legitimately holds `manage_network_connections` in a publishing workspace, *exactly the actor this control targets*, could `POST /rest/v1/network_connection_requests` with the anon key and a session JWT, unlimited, without loading the app. No counter moved, so no alert was written either: the casual clicker was metered and the scripted harasser was invisible. **The PostgREST read-only-transaction argument that makes the directory budget app-side does not transfer to a write** — PostgREST runs a `POST` read-write, which is why the same reasoning reaches the opposite answer here. The meter therefore MOVED into a `BEFORE INSERT` trigger rather than being duplicated: two meters on one click would spend two units and silently halve the limit. A refusal is `PT429` — PostgREST's "return this HTTP status" escape, so a scripted caller gets a real 429 — with the seconds remaining in `hint`. **One deliberate difference from every other category, stated because it is a difference:** this counter does *not* count past its limit. A refused `INSERT` must raise, and a raise rolls back its own increment, so the count is read before the write and a refusal writes nothing at all; "10" here means "hit the ceiling", not "tried n times", and the crossing alert is filed by the last *accepted* request instead of by the first refused one. Q115.

**One mechanism, and the values live in the database.** `public.rate_limit_policies` is the only place a limit's value exists — seeded from this table verbatim and asserted against it row by row (`supabase/tests/rls_phase7_rate_limits.sql` § RV, which fails if a seventh category appears with no row here, or if a number drifts either way). Nothing in TypeScript holds a limit; `lib/security/rate-limit.ts` asks `public.consume_rate_limit()` and obeys the verdict, so the two halves cannot drift the way a mirrored constant could.

**Windows are FIXED, not sliding**, epoch-aligned by `private.rate_limit_window_start()`. The known cost is accepted and stated rather than hidden: **a burst straddling a boundary can reach 2× the limit across 2× the window** (60 discovery reads in the two seconds either side of a minute mark). A sliding window needs per-request timestamps or token-bucket state, which is more machinery than "basic counts only at MVP" warrants.

**Counters keep counting past the limit** — a refused request increments too. The count therefore measures *pressure* rather than permitted traffic (4,000 in a 30-limit window says something a clamped 31 hides), and the alert-at-crossing write depends on the refusing request's own increment committing, which is why `private.record_rate_limit_event()` returns a verdict rather than raising: a `RAISE` would roll back the refusal's count and its own alert row.

**FAIL CLOSED.** A counter write that errors refuses the request, in the app (`lib/security/rate-limit.ts`) and in the auth hook alike — the same direction every other gate in this codebase fails. The metered categories are retryable conveniences, so a false refusal costs a retry, while failing open turns any limiter outage into exactly the unmetered state this section exists to close. A refusal is 429-shaped in the app (`components/list/rate-limit-notice.tsx`, carrying the real remainder) and a distinguishable SQLSTATE at the database — never a silent empty result.

**THE NAMED RESIDUAL: the direct PostgREST path is not metered (Q107).** `GET /rest/v1/network_directory`, issued with the anon key and a session JWT, never enters the Next.js app and therefore never reaches the limiter. This is a measured constraint, not an oversight: **PostgREST executes every GET in a READ-ONLY transaction** (probed on this stack 2026-09-09 — a volatile function reached via `GET /rest/v1/rpc/…` fails with SQLSTATE 25006 "cannot execute INSERT in a read-only transaction", while the identical POST succeeds), and a rate limiter must WRITE, because the increment *is* the mechanism. So no policy term, view or pre-request hook evaluated inside a PostgREST GET can meter that path. The two DB-side shapes that could are both worse than the exposure: replacing the directory views with a POST RPC rebuilds the search path that Q86 forbids and the N2 `pg_depend` lock exists to prevent, and an autonomous-transaction hack (dblink, one extra connection per request) turns the mitigation into a connection-exhaustion DoS. **Recommended closure at Phase 10:** deny the direct-REST path for the two directory views outright via a server-held header checked in `pgrst.db_pre_request` — a DENY needs no write, so the read-only transaction does not block it. Until then the exposure is what Task 3 measured: on a 20k-profile corpus, `display_name` search is a Seq Scan at 44–86ms whose cost is **O(published profiles platform-wide)**, not O(tenant), because RLS's membership `exists` prevents the `ILIKE` from becoming an Index Cond. Also in § 10.

**Two alert types are NOT abuse signals (Phase 8 Task 3).** `dsr_deadline_approaching` and `dsr_overdue` are the platform's own statutory obligation arriving at the operator without anyone opening `/super/data-requests`: `private.raise_dsr_deadline_alerts()` writes them from the SAME `pg_cron` job that delivers the digest, re-pointed by name rather than duplicated (`20260924001000`), immediately before the delivery so an alert raised on a tick is emailed on the same tick. Exactly one per request per stage is a partial UNIQUE INDEX on `(alert_type, details->>'request_id')`, not a `not exists` check two ticks could race, and a closed request raises nothing. The early warning fires 7 days out — a full working week, so it arrives while there is still time to do the work, go back to the requester and get an answer (Q157).

**Incident alerts read these counters.** Three trigger conditions write a platform-scoped `public.incident_alerts` row, superuser-read, shown on `/super/health`: a rate-limit crossing in any category (exactly once per window), repeated failed logins on one account (the login hook's own crossing), and a malware-scan quarantine hit (`private.document_quarantine_alert()`, which deliberately records the document id and never the filename — user-entered content does not belong on a platform surface). `notified_at` is the email seam: null means undelivered, and Task 6's Brevo sender stamps it with no schema change — **which needs a privilege, not only a column**: `service_role` holds `select` on the table and `update` on **exactly two columns and no others** — `notified_at` (`20260909070000`, the operator digest's seam) and `account_notified_at` (`20260916001000`, Q114's separate account-holder seam, which is a different message to a different person and is never folded into the digest). Measured from `information_schema.column_privileges`, not read off the migration. It had neither at first, because `BYPASSRLS` bypasses policies and not table privileges, so the seam had no access path at all. The operator's half is unchanged and the split is the point: a browser session may resolve and may not stamp, the sender may stamp and may not resolve. **The sender is wired (Phase 7 Task 6):** `lib/email/incident-alerts.ts` runs as `service_role` through `lib/supabase/service.ts`, reads `where notified_at is null` (bounded at 200), sends **one digest** through the one Brevo helper, and stamps **only the ids that digest carried, only after `ok:true`** — a failed send stamps nothing and the rows stay re-sendable; a sent-but-unstamped digest is logged and re-sent next run (a duplicate email is the honest failure, a silent stamp over an unsent row the dishonest one). Its entry point is `POST /api/incident-alerts/deliver`, a sessionless route behind `INCIDENT_ALERT_DELIVERY_SECRET` (constant-time compare; **404 when unset or wrong**, so an unconfigured deployment has no endpoint rather than an open one). **The clock is IN THE DATABASE, since Phase 7 Task 6c** — founder ruling Q118: `20260916000000` creates `pg_cron` + `pg_net` and schedules `incident-alert-delivery` every 10 minutes, calling `private.deliver_incident_alerts()`, which `pg_net`-POSTs that route with a bearer read from **Supabase Vault** and never from this repository. Registered locally too, where it is a genuine no-op (no Vault entries → the function returns before it builds a request), so local dev has a clock that ticks and sends nothing rather than a faked send. See § 12 and § 15. **This line said "nothing in the repo calls it on a schedule" for three tasks after the clock shipped**, contradicting `:90`, § 12 and § 15 in this same document — exactly the failure the preamble above calls the worst thing this document can contain, in the direction a pentester briefed on rate limiting would read first. **An alert's `organisation_id` is never caller-supplied**: `public.consume_rate_limit()` accepts one only for organisation-scoped budgets and only after verifying membership (`20260909050000`), because a user-scoped category that passed a caller's organisation through let any authenticated account make the operator's alert feed name an innocent workspace. A user-scoped crossing therefore carries no workspace at all, and `/super/health` says so in words rather than rendering a blank. **But membership is not permission, and the guarantee is exactly that narrow (Q116).** The organisation branch gates on `private.is_active_member()`, and the RPC is granted to `authenticated` and callable straight over PostgREST — so any active member of a workspace, a Read Only one holding neither `manage_network_connections` nor any export right included, can `POST /rest/v1/rpc/consume_rate_limit` against **their own** organisation ten times, deny that workspace connection requests (or exports) for the rest of the hour, and file a `rate_limit_tripped` alert naming their own workspace. That is **in-tenant, not a tenant crossing** — what the check stops is a *stranger*, which is the property finding I1 was about — and it is pre-existing rather than introduced by that fix; it is disclosed here, in `lib/security/rate-limit.ts` and in the function's own comment (`20260909120000`) so the claim reads as "the caller belongs to the workspace" rather than "the caller is entitled to spend its budget". **Resolving and reopening an alert are audited** (`incident_alert.resolved` / `.reopened`, from an `AFTER UPDATE` trigger so a raw `PATCH` is covered too), because the reopen branch nulls `resolved_by` and the row alone could therefore not be the accountability record. SMS is out — Telegram replaces it (founder 2026-09-30, Q111; § 12). Not a full alerting platform: a simple resolved flag, no dedup windows beyond the natural once-per-window crossing, no escalation or acknowledgement workflow.

**THE ALERT FEED IS FLOODABLE, and the mitigation is triage rather than volume (Q117).** Forging an alert's attribution is closed; *filing* alerts is not. One authenticated account can trip the two user-scoped budgets — `search` at 60/min and `network_discovery` at 30/min — roughly **twice a minute, ~2,880 a day**, and every one of those rows is `rate_limit_tripped`, open, and attributed to no workspace, so they are indistinguishable from each other. Two things bound the damage and neither stops the writes: the list is a **keyset pager**, so real alerts stay reachable instead of being pushed off a fixed ceiling, and it carries an **attribution filter** — "Attributed to a workspace" hides the entire flood in one click, because unattributed is exactly its shape — beside the type filter, the status filter and a summary search (the summary is the only place a crossing's *category* appears, since every category shares one alert type). A per-subject dedup window (at most one `rate_limit_tripped` per subject/category per N windows) was the proposed fix and **the founder ruled it OUT on 2026-09-15 (Q117, CONFIRMED AS SHIPPED — no dedup window wanted)**: triage is the answer at this scale, and the attribution filter is the triage. This sentence presented a design that had been declined as though it were the pending correct answer, which is the shape of staleness that invites a future task to re-open a settled decision.

**WHAT IS STILL UNMETERED, so the table is not read as covering everything.** Two write paths carry no budget. The **document-upload action** does real per-call work (byte read, magic-byte sniff, synchronous malware scan) and has no row here at all — its aggregate abuse IS bounded by the per-organisation storage quota (5GB Starter / 20GB Pro), which is not true of any other unmetered path, and picking a per-call number is a founder decision rather than an engineering default (Q113). Every other **CRM write** (creating a contact, an event, a note) is likewise unmetered: each is a small indexed insert inside one tenant, and no measurement suggests a budget is warranted — stated so that its absence reads as a decision rather than an oversight. And the direct PostgREST residual above applies to every `grant`ed table, not only the directory — **and to writes as well as reads, which an earlier version of this paragraph got wrong in the comfortable direction**. A session JWT can *read* any table its policies permit, and *write* any table its policies permit, without passing the app. That is what made the connection-request budget bypassable when it lived only in a server action (above), and it is why the answer there was a database trigger rather than a documented residual: for a **write** the database can meter, because PostgREST runs a `POST` in a read-write transaction. The unmetered-GET residual stands only where a *read* is the thing being counted. The directory is singled out among reads because it is the one whose unit cost is O(platform) rather than O(tenant).

**No `SECURITY DEFINER` search function was built to work around any of this** (Q86's standing constraint — a definer function on the network boundary is the shape that leaks). The limiter is the mitigation; the search path is unchanged.

## 6. File security

The pipeline is built as of Phase 4 Task 5 (`lib/crm/documents.ts` + `lib/security/*` + `app/(app)/[orgSlug]/documents/[documentId]/download/route.ts` + `20260902030000`/`20260902031000`) — upload, authorised signed-URL download, and soft-delete, each audited. The principles below, and how each is enforced as-built:

- **Private bucket, client-fenced.** The `documents` bucket is `public = false` (the primary control — no anonymous public URL exists), and `storage.objects` carries a **RESTRICTIVE deny-all policy** for `authenticated`/`anon` on the `documents` bucket (`20260902030000`). The browser is **never** handed a Storage grant.
- **Server-mediated I/O (Q53).** Every byte in and out goes through a Server Action / Route Handler running the **service-role** Storage client (`lib/supabase/storage.ts`) after the caller has been authorised. The upload action gates on `authoriseOrg(…, 'manage_documents')`, and the database's INSERT policy re-checks the same key — hiding the button is not the control, the refused write is.
- **Malware-scan every upload at MVP.** Behind the `MalwareScanner` interface (`lib/security/malware-scan.ts`). A local **EICAR stub** flags the standard test file so quarantine is fully exercisable on the local stack; a flagged file lands `scan_status = 'quarantined'` and **no signed URL is ever issued for it** (Task 5). The scan is synchronous. **The real engine is self-hosted ClamAV (founder Q42, 2026-10-13):** `MALWARE_SCANNER=clamav` plus `CLAMAV_HOST` selects `ClamdScanner`, which streams the bytes to a clamd daemon over TCP (INSTREAM; nothing written to disk, no file leaves our servers). It is **fail-closed by construction** — any reply other than `stream: OK` / `… FOUND` (refused, timeout, size-limit `ERROR`, empty) throws, and both upload actions turn a throw into `scan_status = 'error'`, which the download gate refuses; a missing host or misspelt provider throws too and never falls back to the stub. The shipped `docker/clamav/clamd.conf` raises clamd's 25 MB defaults (which report a larger file **clean, unscanned**) above the 25 MiB upload cap and sets `AlertExceedsMax` so a limit hit is quarantined. The default with `MALWARE_SCANNER` unset is still the EICAR stub, for dev and test; every deployed environment must set `clamav`. Runbook: `docs/clamav.md`. **Proven:** the wire protocol and every failure path, against an in-process fake clamd (`tests/unit/security/malware-scan.test.ts`). **Owed:** the opt-in live test against real ClamAV (`tests/integration/security/clamav-live.test.ts`, `CLAMAV_LIVE_HOST`) has not yet been run — the dev machine's 2 GB Docker VM cannot hold clamd beside the local Supabase stack; it runs on the first server. See § 10.
- **A strict allowlist by content sniff, not MIME/extension.** `sniffAndAllow` (`lib/security/file-allowlist.ts`) reads the leading **magic bytes** and stores the *sniffed* MIME — a PNG renamed `.pdf` is stored as `image/png`, an `.exe` renamed `.pdf` is rejected. The accepted set is PDF, PNG, JPEG, WebP, GIF, plain text, CSV and the three modern OOXML documents (docx/xlsx/pptx); **macro-enabled OOXML (.docm/.xlsm/.pptm) and executables are rejected** — the OOXML zip family is parsed, not substring-scanned (upload-hardening, 2026-10-13): the **central directory** is read for every part name and `[Content_Types].xml` is **inflated** (capped at 1 MiB, so a zip bomb throws rather than allocates) for every declared type. A `vbaProject.bin` / `vbaData.xml` / ActiveX part, or a content type naming a VBA project, ActiveX or `macroEnabled`, is refused; so is an encrypted entry, a ZIP64 or malformed directory, a missing manifest, or a main part that is not one of the three documents (a `.dotx` template). The earlier raw-byte scan could be walked past — the VBA part may take any name, and the manifest is normally deflated — and `tests/unit/security/file-allowlist.test.ts` carries those bypasses as real zips. **Embedded OLE objects (`embeddings/*.bin`) are still accepted**: legitimate documents carry them, and judging their payload is the real scanner's job, not the allowlist's. The bucket's `allowed_mime_types` is belt-and-braces only; the client's declared Content-Type is untrusted.
- **Downloads are attachments, saved under the sniffed type's extension (upload-hardening, 2026-10-13).** `issueDownloadUrl` signs with Storage's `download` option, so the file is served `Content-Disposition: attachment` and is saved, never rendered inline in a browser tab. The saved name is `downloadFilename(filename, mime_type)`: the display name, with the sniffed type's canonical extension appended when it does not already end in it. Text has no magic bytes, so `payload.bat` or `page.html` is stored as `text/plain` under its own name; it is saved as `payload.bat.txt`, never as something a double-click runs. Asserted on the live header in `tests/integration/documents/upload-scan-download.test.ts`.
- **Sanitised filenames, opaque keys.** `sanitiseFilename` produces a **display-only** name (path stripped, control chars and leading dots removed, length-capped); it never touches the storage key. The key is `buildStorageKey(orgId, documentId)` = `{org}/{doc}` — no filename, no user input — and the DB CHECK `documents_storage_key_shape` makes "inside my own tenant's prefix" a database invariant, so even a bug in the key builder is a 23514, not a cross-tenant file.
- **Every file action is logged.** Upload, download and soft-delete each write an audit row through `public.audit_document_action` (`20260902031000`) — the client-callable thin RPC over `private.log_audit_event` (which stays granted to no client role). A clean upload records `document_uploaded`, a malware hit `document_quarantined`, a download `document_downloaded` (written **before** the signed URL is issued — no audit, no URL), a soft-delete `document_deleted`. Identifiers only (org, document id): no filename, no bytes, because `audit_events` is superuser-readable. See § 7.
- **The feedback screenshot rides the same pipeline, on a second bucket (Phase 7 Task 6).** `feedback-screenshots` is `public = false`, 5 MiB, images only, with the same four **RESTRICTIVE** deny-all client fences (`20260911000000`); bytes go in through `submitFeedbackAction` (service-role Storage client, after `sniffAndAllow` reads the bytes as PNG/JPEG/WebP/GIF — a PDF is refused, a screenshot is an image), are scanned synchronously by the same `getScanner()`, and land on the row as a terminal verdict under an opaque `feedback/{id}` key pinned by CHECK. A quarantined screenshot is stored, never served, and files an `upload_quarantined` alert by trigger with the feedback id and never the message. **A session writer cannot DECLARE a screenshot** (fix round 1, `20260911020000`): the five screenshot columns are in the client INSERT grant because the app writes them after uploading, so on the raw PostgREST path a caller could name `feedback/<own id>` with a `clean` (or `quarantined`) verdict and no bytes; the trigger now requires the object to exist in `storage.objects` for the bucket, or 42501 — so "the row says there is a screenshot" means "the server put bytes there, sniffed and scanned". Bytes come out through one route, `/super/feedback/[id]/screenshot`, which checks the object exists, then audits, then signs — § 4 and § 7.
- **The framework body cap sits above both promises (Phase 7 Task 6 cleanup round, N5).** Both uploads travel as a Server Action body, which Next caps at `serverActions.bodySizeLimit` — **default 1 MB** — *before* the action runs, as a framework 413 and a generic client error. Measured: a 4.9 MiB screenshot behind "up to 5 MiB" and a 2 MB PDF behind "25 MiB" both died there, unseen by every gate because every upload fixture was a few hundred bytes. The cap is now **26 MiB** (`lib/security/upload-limits.ts`, read by `next.config.ts`): the largest promise (documents, 25 MiB) plus headroom for the multipart framing, deliberately above rather than equal to the promise so an upload just over it reaches the action and the *app's* "larger than the N MiB limit" sentence is the refusal the user reads (`feedback.spec.ts` drives a 6 MiB screenshot to it). Above 26 MiB the framework still answers first — a band no screen in the product accepts. Fails closed: nothing over the cap reaches storage. `tests/unit/security/upload-limits.test.ts` holds the cap to both promises so a raised promise cannot silently outgrow it again.
- **The download gate.** `issueDownloadUrl` loads the document **through RLS** (a cross-tenant id or a soft-deleted row returns nothing → 404, no existence leak), refuses anything but `scan_status = 'clean'` (→ 409, the quarantine gate), audits, and only then mints a **60-second** signed URL. The route redirects to it. A `pending`/`quarantined`/`error` document never yields a URL. Soft-delete marks `deleted_at` and audits; the **bytes are deliberately not hard-deleted at that moment** (soft-delete discipline). **Since Phase 8 Task 6 they are purged on a clock** (Q52): `private.sweep_document_bytes()` and `public.retention_object_manifest()` remove the object once the document's parent record's retention class has run out — `financial` (7 years) when it is attached to an event that carries financial entries, `operational` (2 years) otherwise, derived by `private.document_retention_class()` — and stamp `documents.bytes_purged_at`, which is the difference between "we deleted this file because we are no longer allowed to keep it" and "this file is missing and we do not know why". The row survives; the file does not. A **scan-status transition guard** (`before update` trigger) makes a terminal verdict immutable, so a stray PATCH cannot un-quarantine a file — defence in depth behind the fact that only the server sets `scan_status`. **Since `20261029000000` (final review A, I1) "only the server" is enforced by the database, not by convention:** the verdict columns are outside every client grant, `private.guard_document_scan_verdict()` (SECURITY INVOKER, `row_security_active`) refuses any session INSERT not born `pending` and any session change to `scan_status`/`scanned_at` (42501, `document_scan_verdict_is_the_scanners`), and the one writer is `public.record_document_scan_verdict()` — `service_role` alone, refuses a session with a person on it, pending → terminal on one live row — called by `lib/crm/scan-verdict.ts`. Before it, the uploader's own RLS client wrote the verdict, so the uploader's browser could too. Measured: `rls_phase8_retention.sql` § SV (grant, trigger with the grant switched back on, RPC rails, the gate's predicate). The verdict write is sessionless, so it files no `document.updated` row; the upload's `document_uploaded`/`document_quarantined` row carries the uploader. The feedback screenshot path has no pending window (scan, then one INSERT, server-chosen id) and keeps `20260911020000`'s bytes-must-exist rule.

## 7. Audit logging

- Every high-value action records: actor, org, timestamp, action, target, correlation ID, before/after values.
- Append-only from the application. Superuser access audits itself. Passwords, tokens and keys are never logged.
- Retention: hot/queryable for 30 days, archived (cold storage) for up to 1 year total, then purged. Deletion/alteration of audit records outside that lifecycle is restricted to a narrowly controlled platform security process.
- **Consent events are audited (Phase 8 Task 2):** every grant and withdrawal writes `consent.granted` / `consent.withdrawn` from an `AFTER INSERT` trigger, with no organisation (consent is account-level) and a payload of identifiers and enums only — purpose, category, policy slug and version, mechanism, and for a withdrawal the grant it ended. Never the wording shown or any technical context (`rls_phase8_consents.sql` § CA).

### CRM writes: what is audited today, and what is not (Phase 2, fix round 1)

**Audited in the database, by trigger, so a direct PostgREST call cannot avoid it:** the two hard `DELETE` paths Phase 2 opened (`contact_companies`, `custom_field_values`) and every `merges` insert (`20260828141000`). A trigger rather than application code, for the same reason the `updated_at` trigger exists: `grant … to authenticated` plus the anon key that ships in the browser makes `DELETE /rest/v1/contact_companies?id=eq…` reachable without touching the Next.js app, so an application-side audit records only the deletions someone remembered to route through it.

**Every CRM `INSERT` and `UPDATE` is audited too, since Phase 7 Task 6b (`20260912000000`).** This paragraph used to say "not audited yet" and route the work to Task 6b (Q94); it shipped. The same trigger shape, on all eleven mutable Phase 2 tables (`companies`, `contacts`, `contact_companies`, `agencies`, `artists`, `artist_representations`, `artist_fee_history`, `venues`, `venue_rooms`, `custom_field_definitions`, `custom_field_values` — `merges` is append-only and its one `INSERT` was already audited), `AFTER INSERT OR UPDATE FOR EACH ROW`, so a raw `PATCH /rest/v1/contacts` is covered exactly as the form is. Four actions per table — `<target>.created`, `.updated`, `.soft_deleted`, `.restored` — with the last two distinguished at the trigger from a `deleted_at` transition so a soft-delete is never buried as "updated"; `soft_deleted`, not `deleted`, because `contact_company.deleted` and `custom_field_value.deleted` already mean a hard delete. Forty names, all in the viewer's catalogue (`lib/admin/audit-actions.ts`, offered by the Action filter as a `<datalist>`) and bound to the live `pg_trigger` arguments by `tests/integration/admin/audit-actions-match-db.test.ts`.

**The diff design — what an UPDATE row carries without breaking the no-content rule above.** `after.changed` is the sorted list of every column whose value changed (`updated_at` excluded, since the `BEFORE` trigger moves it on every write); `before.values`/`after.values` carry old and new **only for a per-table allowlist of structural columns** — ownership/assignment ids, foreign keys, booleans, dates, `deleted_at`, and `CHECK`-constrained closed vocabularies (`companies.type`, `entity_type`, `field_type`, `currency`). For everything else — name, email, phone, title, location, website, socials, tags, genres, country, city, notes, address, capacity, technical info, role, territory, fee amounts, custom-field keys, labels, options and values — the row says "`notes` changed" and never what it changed to. The allowlist is **one function**, `private.audit_crm_value_columns(target_type)`, and it is the only thing the trigger reads to decide what it may copy, so a column added later is name-only until someone edits that function and justifies the addition in the migration header — fail-safe, where a denylist would have leaked the new column on the day it shipped. An `INSERT` row carries the same projection over the whole new row. A no-op `UPDATE` (nothing but `updated_at` moved) writes no row. **The property is measured, not asserted**, from three positions per table: `supabase/tests/rls_phase7_crm_audit.sql` § CU (a member's session in psql), `tests/integration/security/crm-audit-no-content-leak.test.ts` (a real member's supabase-js client over PostgREST), and `tests/e2e/audit-log.spec.ts` (the real edit form, then the founder's screen) — each writes a sentinel into a content column and searches the audit row's whole `before`/`after` for it.

**The exemption, and why it is `auth.uid()`.** The trigger writes nothing when `auth.uid()` is null: migrations, seeds, DBA repair and the cascades they start (`ON DELETE SET NULL` on `owner_user_id` fires an UPDATE with no session). No client path is exempt — `service_role` holds no grant on any of the eleven tables (measured, § CX3). It is `auth.uid()` and **not** `row_security_active()`, because the latter is false inside every `SECURITY DEFINER` function and would have silently skipped any write made from inside one (Task 5 I4's lesson, re-proved here: § CX2 writes from inside a definer and reads the row back).

**Bulk paths share one thread.** The four multi-row RPCs — `merge_records`, `set_contact_primary_company`, `set_artist_primary_representation`, `set_custom_field_values` — would each have sprayed one freshly-minted `correlation_id` per touched row. `20260912001000` reuses Task 3's threading mechanism through a **second GUC** (`app.crm_bulk_correlation_id`, consulted by `log_audit_event()` as a fourth coalesce step) rather than the lifecycle marker, because that marker is also the second term of `organisations_update_platform_lifecycle` and a member must not be able to set a policy term. Each RPC's body was **moved** to `private.<name>_unthreaded` and wrapped under its original name, so the only routable merge is the threaded one (the runner's HTTP block asserts the moved bodies are 404). A merge now reads as one thread: the winner's `contact.updated` naming `phone` and not its value, the loser's `contact.soft_deleted`, every repointed link's `contact_company.updated` (old and new `contact_id`), every carried or swept custom-field value, `records.merged` and `records.merged.fields` — measured in § CB.

**Volume and retention — Q94's second question, answered with numbers.** One row per `INSERT`, one per effective `UPDATE`. A `contact.updated` row with one changed column is **221 bytes of heap** (5,000 rows = 1,080 kB, measured on the 5,000-row bulk fixture) — but **472 bytes** once `audit_events`' six indexes are counted, and **472 is the figure any volume projection must use**. This paragraph previously quoted the heap number alone, as "216 bytes", which understates real storage by more than half. Worked at the honest rate: 100 workspaces averaging 200 audited CRM writes a day is 20,000 rows/day ≈ 9.4 MB/day — roughly **283 MB across the 30-day hot window** and **3.4 GB by the 1-year archive boundary** the purge job enforces. On the golden path, each Phase 2 step (create contact, company, link, artist, venue, room) writes exactly one `.created` row beside its record, a primary-company change writes two `contact_company.updated` rows on one thread, and the Phase 3/4 steps (event, lineup, task) wrote none until Phase 8 Task 7 — they write one row each now; see the Phase 3–6 paragraph below for the measured number. **Measured end to end rather than asserted:** a walk of eight inserts, an edit, a primary-company change, a soft-delete, a restore, an edit-while-deleted and a restore-with-rename produced **16 audit rows across 15 distinct correlation ids**, with no sentinel leak anywhere in them. Note what that thread count means in practice: only the RPC's pair shares an id, so "one correlation id per user action" describes a multi-row RPC and **not** an ordinary form save, which is several requests and therefore several threads. The audit table therefore grows at roughly the rate of the tenant tables it watches — an audit row is smaller than the record it describes — and CLAUDE.md's 30-day hot / 1-year archive lifecycle bounds it; the purge job that implements that lifecycle is the same Phase 8 machinery every other retention clock in this product waits on (Q120). **No per-table opt-out is built**, deliberately: it would be speculative infrastructure for a volume nobody has measured as a problem, and an opt-out is a hole in the audit trail with a switch on it. If a tenant's write rate ever makes this material, the shape to add is Task 3's — threading plus a summary row, or suppression as one more branch in `log_audit_event()` — not a switch per table. **Performance:** a row-level trigger on every write costs **~0.36 ms per row** (5,000-row bulk `UPDATE` as a member: 2,177 ms with the trigger, 395 ms without — the difference is `log_audit_event()`'s definer call, the jsonb diff, the organisation lookup and six index inserts). Per request that is invisible; for a bulk operation it is the price of the evidence, and stated. (An independent re-measurement on a contended machine gave 3,407 ms against 552 ms — 0.57 ms/row — so treat 0.36 ms as the floor rather than a constant.) **The whole-suite `pnpm test` before/after that the same requirement asks for is NOT measurable on this machine, and no number is offered for it:** identical code ran **178 s and 1,908 s** on two runs, and the pre-task tree ran **406 s**, the spread tracking free memory (3+ GB versus under 1 GB, with a second Supabase stack up) rather than anything in this change. The isolated per-row cost above is the honest answer.

**The viewer's action filter gained `audit_events_action_created_at_id_desc_idx` `(action, created_at desc, id desc)` — and it is a bet on scale, not a win this product's row count can demonstrate.** This paragraph previously claimed the filtered keyset page was "an Index Only Scan, 28 buffers / 0.06 ms, against 288 buffers / 1.99 ms without it". **That claim is withdrawn: it was wrong twice over.** An Index Only Scan is structurally impossible for this query — `fetchAuditLogPage` selects `before`/`after`, and a `(action, created_at, id)` index cannot cover a jsonb column — so the quoted plan cannot have come from the viewer's query at any size. And re-measured with `EXPLAIN (ANALYZE, BUFFERS)` on that function's real select list after `ANALYZE`, the numbers do not reproduce. What is actually true, measured: **at 5,000 rows the planner never chooses it.** A common action (99% of rows) walks `audit_events_created_at_idx` backward with a filter (4 buffers, 0.12 ms); a rare one (0.5%) uses `audit_events_action_idx` and sorts (27 buffers, 0.24 ms); dropping the composite index changes neither plan nor buffer count. **At 200,000 rows the planner does choose it, for a rare action** — 52 buffers and 0.15 ms, against 1,028 buffers and 1.21 ms for the `action`-index-plus-top-N-sort it falls back to without it: ~20× the buffers and ~8× the time, and that gap widens with the table. For a *common* action it is chosen at neither size, because walking the `created_at` index and discarding non-matches reaches a page of 25 almost immediately when nearly every row matches. **The index is kept on exactly that evidence** — its write cost is already counted in the 472 bytes above, and it pays for itself on rare-action queries once the table is large, which is the direction CRM write auditing takes it. Today it is a projection, and this section now says so.

**The Phase 3–6 tables are audited too, since Phase 8 Task 7 (`20261006000000`, Q122).** This paragraph used to say "What is NOT covered … carry no `INSERT`/`UPDATE` audit" — a raw `PATCH /rest/v1/events` by a valid member left no trace at all. The same trigger function and the same allowlist now cover **sixteen more tables**: `events`, `event_lineup`, `tasks`, `meetings`, `notes`, `documents`, `task_links`, `meeting_links`, `note_links`, `document_links`, `financial_entries`, `network_profiles`, `network_links`, and three that no list named and the DERIVED census found — `organisation_memberships` (an invite, a **role escalation** and a removal all left no row; removal is a hard `DELETE` and is `membership.deleted` through `audit_crm_row()`), `organisation_subscriptions` and `merge_candidates`. **Structural columns only**, and the withheld set is named in the migration header: never `notes.body` (a PRIVATE note's text on the superuser's screen is the exact boundary Q54 protects), `meetings.attendees`, `documents.filename` (typed by the uploader, routinely a person's name) or `storage_key`, `financial_entries.amount_minor`/`description`, any published network-profile value, or `merge_candidates.label`. **The list is derived, not declared:** `private.audit_coverage()` enumerates every table in `public` with a foreign key to `organisations` (or `organisations` itself) on which `authenticated` or `anon` holds `INSERT`, `UPDATE` or `DELETE` at table **or column** level, and classifies each operation as covered by the generic pair, by a dedicated `private.audit_*` `AFTER ROW` trigger, or by marker-guarded policies (RPC-only writes); `tests/integration/admin/crm-audit-coverage-census.test.ts` binds that to `CRM_AUDIT_TARGETS` and `AUDIT_COVERAGE_EXCUSALS` in both directions, and is red by NAME for a planted table and for a real trigger dropped (mutation: `drop trigger audit_update on public.tasks` → "Uncovered: organisations:UPDATE, tasks:UPDATE", nine red across three files). **Since that task's fix round 1 (`20261007001000`, review M1/M2) a trigger counts only when it is ENABLED** (`pg_trigger.tgenabled` `O` or `A`) -- before it, `alter table public.tasks disable trigger audit_update` left every census test green; the marker-guarded (RPC-only) class requires row security to be ON; and the denominator also takes a table with an `organisation_id` column but no direct foreign key, and a client-writable auto-updatable view (which can only read `unaudited`). **Its stated limits:** a trigger's `WHEN` clause is not read (`feedback` and `incident_alerts` each have one, both legitimate); a table only a SECURITY DEFINER function writes has no client grant and is outside the denominator by construction -- `merge_candidates`' INSERT is exactly that (`screen_for_duplicates()`), so disabling its `audit_insert` reds nothing in the census and is caught only behaviourally (psql § PQ); and it sees that a trigger FIRES, not what it DOES — it rated `network_profiles` covered by a writer that returned early for every ordinary edit — so the behavioural half is `supabase/tests/rls_phase8_crm_audit_p3_6.sql` (204 assertions since Task 7's fix round 1, 186 as shipped: one row per verb per table with actor, organisation, target type and allowlisted keys; **The audit payload is an allowlist of identifiers, never user-entered content.** `private.audit_crm_payload()` projects each audited row down to its identifiers and structure and drops `custom_field_values.value` and `merges.field_resolution`. `audit_events` is readable by exactly one principal — the platform superuser — and `CLAUDE.md` § Superuser dashboard keeps tenant record content off that surface, describing the in-app feedback screenshot as *the one* deliberate exception. If restore is wanted it needs a founder decision about superuser access to tenant content, or a tenant-scoped undo table rather than `audit_events`.

**Sessionless writers emit no audit row.** The trigger returns early when `auth.uid()` is null, because `private.log_audit_event()` raises `28000` on a null actor and an unconditional trigger would abort `DELETE FROM organisations` (which cascades into both audited tables with no session). What that excludes is migrations, seeds, DBA repair and the cascades they start — not any client path, since `service_role` holds no grant on these tables.

### Impersonation: every transition AND every page reached (Phase 7 Task 2)

**Six audited actions on `target_type = 'impersonation_session'`:** `impersonation.requested`, `.accepted`, `.declined`, `.started`, `.page_viewed`, and `.ended`/`.expired` (`20260908020000`). The first five transitions are written **inside the same `SECURITY DEFINER` RPC that performs the transition**, in one transaction — so a state change that is not audited is a state change that did not commit. That is stronger than either of the two shapes above and is warranted: this is the only path by which a non-member reads a tenant.

**The session id is the correlation key.** `private.log_audit_event()` mints a fresh `correlation_id` per call unless given one; every row this flow writes passes the session id, so `select * from audit_events where correlation_id = <session id> order by created_at` is the complete, ordered story of one impersonation — request, consent, start, every route reached, end — with no join. `target_id` carries the same value deliberately: `correlation_id` is the thread, `target_id` is what the row is *about*, and the audit log viewer filters on different ones of those. Every row also carries `organisation_id` = the **target** organisation, so an impersonation surfaces to anyone filtering that tenant's events, and `actor_user_id` = the **real** actor — `log_audit_event` forces `auth.uid()` and accepts no override, so the accept row names the admin who consented and the rest name the superuser. Nothing in this feature borrows an identity.

**Page access is audited APP-SIDE, at the resolver, and the placement is the decision.** `public.audit_impersonated_page_view(org, route)` is guarded by **the grant itself** (`private.impersonated_organisations`), so a caller with no live session mints no row; the app calls it from `lib/admin/impersonation-session.ts`'s `resolveImpersonationForOrg()`, which `getCurrentOrg()` reaches on **every** org-scoped page. A layout-level audit would have recorded the first page of a session and none of the rest, because an `[orgSlug]` layout does not re-run on a client-side navigation between two routes that share it. **It fails closed**: a refused audit write returns "not impersonating", and the route renders the ordinary tenant-isolation 404 — there is no path that serves an impersonated page without a matching audit row. **It over-records rather than under-records**, and that is the deliberate opposite of the audit-log viewer's own prefetch decision (Task 1): a Next.js prefetch of an org route renders the layout and therefore lands a `page_viewed` row for a page nobody read. A trail listing a route nobody opened is noise; one missing a route somebody did open is a hole in the product's only deep-access path.

**ROUTE ONLY, NEVER CONTENT.** The RPC's signature has no parameter that could carry a record name, a search term or a result count, and the app strips the query string before calling (`auditableRoute()` in `lib/admin/impersonation-contract.ts`) — `?q=` is where a list page's search term lives, and a search term is a fragment of what the tenant's records say. A path **segment**'s record id is deliberately kept: knowing which record support opened is the entire point. `rls_phase7_impersonation.sql` § IA6 asserts the `after` payload's key set is exactly `{route}`.

### Organisation lifecycle: one summary row per transition, and a general threading mechanism (Phase 7 Task 3)

**Three audited actions on `target_type = 'organisation'`:** `organisation.suspended`, `organisation.deleted`, `organisation.reinstated` (`20260908030000`). Each is written by `private.log_organisation_lifecycle_event()` in the same transaction as the transition, so a state change that is not audited is a state change that did not commit — the impersonation shape above, for the same reason: these are the operator's most consequential actions on a customer.

**The `after` payload is a SUMMARY, and it is counts, never rows.** New state, `lifecycle_changed_at`, `retention_expires_at`, the operator's verbatim reason, the subscription period end that governs network presence, and COUNTS of what the transition touched (active members, published profiles). No name, no email, no record id — so this stays inside `CLAUDE.md` § Superuser dashboard's "aggregate metadata, never record content", the same discipline `rls_phase7_impersonation.sql` § IA asserts for the impersonation rows. `rls_phase7_lifecycle.sql` LA5 asserts it directly.

**THE CASCADE-AUDIT ANSWER, and it is deliberately general.** `FOLLOW-UPS.md` had an open question about the organisation-delete path emitting one audit row per cascaded child, each with its own `correlation_id`, because `private.log_audit_event()` mints a fresh one per call. That function now resolves the id in **three** steps rather than two: an explicit `p_correlation_id` wins, then the thread `private.begin_lifecycle_transition()` declares, then — unchanged — a fresh uuid. **An operation declares itself once and every audit row written anywhere inside it, by any trigger including one added years later, joins one thread with no call site edited.** `private.end_lifecycle_transition()` closes it, and the pairing is not optional: an `is_local` GUC stands to the end of the *transaction* whatever `SET` clauses the call stack carries. **Suppression was considered and rejected** — it discards evidence to save space, in the table whose purpose is evidence, and unrecoverably. **Phase 8's hard purge and the DSR erasure must reuse this** rather than inventing their own: declare once, do the work, write one summary row.

**The operator's reason is CUSTOMER-VISIBLE, deliberately and with a test.** `organisations.lifecycle_reason` sits on a table every active member can read (`organisations_select_member`); RLS filters rows and not columns, and Postgres column privileges are per-ROLE — the superuser and the customer are both `authenticated` — so hiding it from the workspace while showing it to the operator is not an available arrangement. Task 3's self-review found the first cut disclosing it through PostgREST while the banner hid it, which is the worst of the three options; the product now renders it on the banner and both operator forms warn in the field hint. `rls_phase7_lifecycle.sql` LA5a/LA5b assert a member reads it and a foreign Owner does not. **An operator must not put anything in that field the customer may not read**; an internal-only note would be a second column no member-facing query projects (DECISIONS-QUEUE Q103).

**The marker is also a security control, not only an audit one.** `private.lifecycle_transition_in_progress()` is the second term of `organisations_update_platform_lifecycle`, so a raw `PATCH /rest/v1/organisations` from the superuser's own browser — who is on the allowlist, at aal2, and can read the row — matches nothing. That is what makes "every lifecycle transition is audited with a reason" structurally true rather than conventionally true. It is not a boundary against a hostile superuser; nothing in this schema is.

### An Owner closes their own workspace (Phase 8 Task 9c; founder 2026-09-30, Q176/Q178, reversing Q104)

### In-app feedback: three audited actions on `target_type = 'feedback'` (Phase 7 Task 6)

**`feedback.submitted`** and **`feedback.status_changed`** are written by triggers (`private.audit_feedback_submission()`, `private.audit_feedback_status_change()`, `20260911000000`) — the CRM hard-delete reasoning, because `public.feedback` carries a client INSERT grant and a client UPDATE(status) grant, so a raw PostgREST `POST`/`PATCH` is a real path no call site could cover. ### Document actions: audited APP-SIDE, and why that differs from CRM writes (Phase 4 Task 5)

**Three new audited actions, on `target_type = 'document'`:** `document_uploaded`, `document_downloaded`, `document_deleted`, plus `document_quarantined` for a malware hit (`20260902031000`). Each is written by the application — the upload/delete Server Actions and the download Route Handler — through `public.audit_document_action`, a **thin client-callable RPC** over `private.log_audit_event`. The private writer stays granted to no client role; the public wrapper is the only reachable surface and it is **guarded**: the caller must hold `view_crm` in the org **and** the document must really belong to that org, so a forged RPC call cannot mint audit rows for orgs or documents the caller has no relationship with (the actor is always forced to `auth.uid()`).

**APP-SIDE, not a trigger — the opposite decision from the CRM hard-delete audit above, on purpose.** The CRM audit is a trigger because `grant … to authenticated` plus the browser's anon key makes a raw `DELETE /rest/v1/contact_companies?id=eq…` reachable **without the app**, so the database is the only chokepoint. A document's **bytes have no such second path**: `storage.objects` for the `documents` bucket is deny-all fenced to every client role (`20260902030000`), and the only principal that can read or write a `documents` object is `service_role`, on the server. There is no PostgREST-reachable "download this file" endpoint to bypass — an upload is a Server Action and a download is a Route Handler, and both run the audit before they touch Storage. So for documents the **application is the only path in and out**, and an app-side audit is sufficient and correct. The **download audit in particular is written before the signed URL is issued** (`issueDownloadUrl`), so a logged access is a precondition of a served file, not a side effect of it. The metadata row *is* client-reachable, but a metadata write is not the audited event — the sensitive action is the movement of bytes, which is server-only; the scan-status transition guard is the metadata-side defence in depth.

### Deleting audit rows: the one narrowly controlled process, as built (Phase 8 Task 6)

`CLAUDE.md` promises the audit log is "hot/queryable for 30 days, archived
(cold storage) for up to 1 year total, then purged", and until Phase 8 Task 6
nothing applied either limit. Both are applied now, and the two halves are
different things:

- **"Hot for 30 days" is the VIEWER'S DEFAULT RANGE, not a storage boundary**
  (founder ruling Q135). `/super/audit-log` applies a 30-day floor when the
  operator supplies no `from` date, and says so on the page — a silent default
  makes "the log does not go back that far" and "we are only showing you a
  month" look identical, and only the second is fixed by typing a date.
  Setting `from` reaches straight past the floor. `AUDIT_HOT_WINDOW_DAYS` is
  the one retention period that had to leave the database (a PostgREST query
  cannot call a `private` function), and
  `tests/integration/rls/retention-matches-db.test.ts` binds it to
  `private.retention_periods()`'s `audit_hot` class.
- **"Archived" means the rows are still in Postgres.** There is no cold store
  and the public page says so. At one year they are deleted.

**`private.purge_audit_events()` is the deletion, and it is the most dangerous
code in this phase** — it destroys the evidence that the product did what it
says it did, and an audit log that has been wrongly emptied cannot be noticed
by reading it. Five rails, each independently mutable and each with its own
refusal hint so that "the floor refused", "the ceiling refused" and "a
privilege was missing" cannot be confused with one another:

1. **A HARD FLOOR of one year that no configuration can lower.** Compared
   against `private.audit_retention_floor()` AND against the purge's own
   literal, so editing either alone does not move it. If
   `private.retention_periods()` ever declares a shorter `audit_total`, this
   REFUSES (`55000` / `audit_retention_below_floor`) rather than obeying it.
   That is the difference between a floor and a default.
2. **Its own kill switch**, `public.retention_settings.audit_purge_enabled`,
   asked before anything is counted and separate from the master switch —
   "stop deleting audit rows until we know the clock is right" and "stop
   reaping stuck export jobs" are different decisions.
3. **A SANITY CEILING**: a run that would delete more than a fifth of the
   table, when that is also more than a thousand rows, refuses
   (`audit_purge_over_ceiling`). At steady state a run deletes ten minutes'
   worth of rows; a fifth means the clock, the declared period or the column
   is wrong, and a job that has deleted nothing yet is recoverable while one
   that has deleted a year is not. **It has a release since Phase 8 Task 9a**
   (`20261010000000`, Q184, founder 2026-09-30): `public.release_audit_purge_ceiling()`
   — the aal2 superuser only, a mandatory reason, audited as
   `retention.audit_ceiling_released`, on `/super/health` beside the kill
   switches — lifts THIS rail alone for exactly 72 hours and lapses by
   read-time expiry (`private.audit_ceiling_release_active()`; nothing
   reverts it). One at a time: a second release while one is active is
   refused, not extended. Rails 1, 2, 4 and 5 still apply under a release, so
   the most a release can let through is 72 runs × 500 rows = 36,000 rows,
   every one already past the declared (≥ 1 year) period
   (`rls_phase8_retention.sql` § RL-REL, REL1–REL28).
4. **A per-run ceiling, oldest first, resumable** — a backlog drains in order
   rather than locking the table, and `capped` in the run log says one exists.
5. **The totals before and after**, counted in the same transaction as the
   delete, so the run log's arithmetic is checkable rather than trusted.

Plus a **dry run** over the same query, which is what makes the rails usable:
the founder can ask what a run WOULD delete, from `/super/health`, and get the
numbers with nothing removed.

**It exempts no action, deliberately.** An exemption list for "actions too
important to delete" is a retention policy written twice, and only one of the
two is on the published page. If some actions should be kept longer, that is a
class in `private.retention_periods()` and a sentence on
`/legal/data-retention`.

## 8. Data retention and residency

- Soft-delete operational records rather than hard deletion, subject to retention policy.
- Working defaults (pending legal sign-off — see `CLAUDE.md` § Legal and regulatory compliance): **7 years** for financial records, **2 years** for inactive-account data (also applied to in-app feedback submissions — see `CLAUDE.md` § In-app feedback), **30 days hot / 1 year archived** for audit logs.
- **Feedback retention is enforced at READ time (Phase 7 Task 6):** `feedback_select_platform` carries `created_at >= private.feedback_retention_cutoff()` (now − 2 years), and the screenshot-view RPC re-tests the same cutoff, so an expired row is unreadable on every path — the app, a direct PostgREST GET, the signed-URL route — with nothing scheduled (the Q88 / Task 4 pattern). Measured: `rls_phase7_feedback.sql` FR6/FA7. **Since Phase 8 Task 6 the rows and their screenshot bytes ARE purged** (Q120): `private.sweep_feedback()` deletes an expired row, and the runner removes the `feedback/{id}` object first — the row sweep REFUSES a row whose screenshot is still in the bucket, because deleting it there would leave an untracked image of somebody's screen that only the orphan sweep would find, a day later. A submitter's account erasure cascades to their feedback rows (`on delete cascade`, unlike `audit_events`), so a DSR does not wait on that job.
- **The public Data Retention Policy (`/legal/data-retention`, Phase 8 Task 1) states these working defaults as pending counsel.** Its version 4 said in words that the automated deletion job was not running; **version 5 (`20261003009000`) says it runs, and says what that does and does not mean** — about hourly, bounded per run so a backlog drains over several, a failed deletion retried rather than forgotten, so a record can outlive its period by hours. **Version 5 OVERCLAIMED, and version 6 (`20261004006000`, Task 6 fix round 1, review finding I3 / Q183) is the correction:** deleting "Automated deletion is still being built" removed the shield over "Inactive account data: 2 years" (nothing sweeps it — Q180 says deliberately not), over "when a period ends, the data is permanently deleted or anonymised" (false for every table `private.retention_subjects()` calls `retained_with_workspace` — a soft-deleted contact is kept for as long as its workspace exists, by design) and, found by the sentence-by-sentence check rather than by the review, over "Financial records: 7 years", which read as a deletion date and is not one. Version 6 has a section saying plainly what is **NOT** automatically deleted, states all eleven declared periods including the 90 days for a FAILED account deletion, and is bound so it cannot drift the same way again: `rls_phase8_retention.sql` § RL finds every declared period on the page in the sentence that states it with the DATABASE'S number (so counsel's answer to Q133 reds the page until it is corrected too) and every `retained_with_workspace` table in the not-deleted list. It also keeps saying there is no separate archive store, because there is not: "archived" means the record stays in the same database and falls out of the operator's default 30-day view (Q135), which is less than the word suggests. **Its version 1 described an audit "default view" that does not exist** — neither `audit_events_select_platform_superuser` nor `/super/audit-log` applies any time window, so every audit row is searchable for as long as it is stored; version 2 (`20260922005000`) states the 30-day/1-year windows as the target Task 6 will apply. **The public Security and Trust page follows one rule since the same migration:** every control this § 15 lists as hosted configuration is marked "(deployment setting)" there, and the host's encryption/TLS is attributed to Supabase as unverified.
- **Export archives are a new store with a seven-day clock, and READ-TIME EXPIRY is only half of it (Phase 8 Task 4).** `public.export_jobs.expires_at` is `completed_at + private.export_limits().archive_days`, stamped by the database, and the download path refuses a job past it — so after seven days the archive is unreachable by everyone including its own requester, with nothing scheduled (the Q88 pattern). **Task 6's retention job now removes the BYTES too**: `public.retention_object_manifest()` names every archive past its own `expires_at`, and the runner deletes it. Before that, every archive anyone had ever taken was still in the bucket — measured, not assumed: there was no other caller of `remove()` for that bucket anywhere in the repository. The two orphan classes join the same job and are covered by the same manifest's ORPHAN half — the object of a job whose requester's account is deleted (the ROW cascades, the bytes do not), and the object of a job that uploaded and then failed to stamp — through a sweep of objects no row names at all, older than a one-day grace period. The grace period is not caution for its own sake: an upload writes the object and THEN the row, so for a fraction of a second every healthy upload is an orphan.
- GDPR data subject requests (export/erasure): **30-day** target, matching the ICO statutory maximum.
- **The ACCESS and PORTABILITY half of that is now a real job rather than a promise (Phase 8 Task 4), and the register enforces it.** `private.dsr_fulfilment_job_ready('export')` answers `true` from `20260927003000`, so an account-scope `access` or `portability` request can no longer be marked fulfilled by hand: an export job for that requester must have completed **after the request was made** and recorded itself on the row, or the transition is refused (22023, hint `fulfilment_not_recorded`). The seam is written by the runner as `service_role` through a **two-column** `UPDATE` grant (`fulfilment_kind`, `fulfilment_reference`) and nothing wider; `fulfilment_recorded_at` is stamped by the trigger and is deliberately outside the grant. `private.dsr_fulfilment_job_ready('erasure')` is still `false` — Task 5.
- **Since Phase 8 Task 3 that 30 days is a deadline the DATABASE computes and alerts on, not a target.** `public.data_subject_requests.due_by` is a `GENERATED ALWAYS` column — `requested_at + 30 days`, unwritable by every role including `postgres` (428C9) — and `requested_at` is stamped by the `BEFORE INSERT` trigger, so neither end of the window can be moved by a client, an operator or a repair script. Every state change goes through one `BEFORE UPDATE` trigger that is the transition table, the who-may-do-it check and the stamper at once (`private.data_subject_requests_before_update`); nothing is enforced only in a server action. See § Data subject requests below.
- **ERASURE IS THE OTHER HALF, AND IT IS A HARD DELETE (Phase 8 Task 5).** Everything above is soft-delete-then-retain; account erasure is the one path in the product that is not. `private.erase_account()` is a single `security definer` function, one transaction, ALL-OR-NOTHING: any refusal rolls the whole sequence back and the job is recorded `failed` with a reason, so there is no state in which part of an account is gone. It is IDEMPOTENT (a second run answers `{"already_erased": true}`), it REFUSES to run under any `session_replication_role` but `origin`, and it REFUSES while a byte of the account's stored objects is still in its bucket — Storage lives outside Postgres, so the runner sweeps it first and the database will not let a row delete be the thing that makes an object unreachable-but-present.
- **THE AUDIT TRAIL IS PSEUDONYMISED, NEVER DELETED (Q130).** THIRTEEN foreign keys reference `auth.users` with no `ON DELETE` action — measured on the live catalogue at 164 migrations, against the inventory's "eight-plus" — and every one is rewritten to a single platform-owned TOMBSTONE identity (`private.erased_user_id()`, `00000000-0000-4000-8000-0000e7a5ed00`, created by a migration and not by application code). It can never sign in, never hold a membership or a `platform_admins` row, and never be deleted; all three are enforced by triggers rather than asserted. **The rewrite is DERIVED from `pg_constraint` at run time, not listed**, and the same walk asserts afterwards that no reference of any kind survives — so a fourteenth blocking key added by a later phase is handled on the same deploy, and a COMPOSITE one (which the single-column walk could not see) raises rather than being skipped. One tombstone for everybody on purpose: a per-person tombstone is a per-person identifier, and an identifier that survives erasure is not erasure.
- **What an erasure does NOT delete, and why each is deliberate.** A workspace's CRM records: Q132 makes the customer their controller, so a member's departure nulls the ownership columns and leaves the records (`SECURITY.md` § 2's tenancy rule, not a retention one). `financial_entries`: `created_by` goes null by the foreign key and the entry stays inside its 7 years. The DATA SUBJECT REGISTER and its operator notes (Q158, CHANGED from cascade): re-pointed at the tombstone with `user_email`, `detail` and any rejection reason replaced by `[erased]`, because under the cascade the erasure job would delete the row its own outcome has to be recorded against. **Consents ARE deleted, by the shipped cascade, and that is a departure from Q158's sibling treatment with a measured reason** — `public.consents` is an alternating chain per (user, purpose) with a unique `withdraws_id`, and merging two erased people's ledgers onto one tombstone produces a history the table's own rules say cannot exist. Q173 puts it to counsel.
- **What it deletes that a null would not.** A PRIVATE note whose owner is nulled is readable by nobody and stored for ever, which is burial rather than erasure, so private notes are HARD-deleted; a `company` note is the workspace's and stays with a nulled author. The stores holding a user id that NO foreign key protects are cleared **from a pinned roll the catalogue is made to agree with** — `private.fkless_identifier_columns()`, every uuid column in `public`/`private` that is in no foreign key and is not its own table's primary key, classified and given a treatment, with `private.assert_fkless_identifier_roll()` refusing the erasure outright when a new one is unclassified (Task 5 fix round 1, review finding C1: the hand-written version named `merges` and not `merge_candidates`, whose two owner-id snapshots `screen_for_duplicates()` writes on every flagged duplicate, and a column in no foreign key is invisible to both of the function's derived assertions). Closing it properly — a transaction-local GUC the chokepoint sets, in `private.begin_lifecycle_transition()`'s shape, so the cascade FAILS instead of stranding — is **Q179**, deferred because it turns every fixture and suite that deletes an auth user into a refusal.
- **What the C2 lock costs, measured (Task 5 fix round 2, N4).** `private.account_lock_workspaces()` holds `FOR UPDATE` on every membership row of every live workspace the subject is an active member of, plus one advisory transaction lock each, for the **whole** erasure transaction — so every concurrent role change, revoke and removal in those workspaces blocks until it commits or rolls back. INSERTs are not blocked, so invitations still work. ### The retention job, as built (Phase 8 Task 6)

**One `pg_cron`-scheduled job, not a second clock.** The product still has
exactly one scheduler and one job — `incident-alert-delivery`, every ten
minutes — and the retention sweep is its **fifth half**, after the erasure
runner, the export runner, the data-subject-request deadline alerts and the
incident digest. Each half is its own subtransaction, so none can take another
down, and `rls_phase8_retention.sql` § RC14 pins all five BY NAME: a Phase 7
alert type or a Task 4 runner dropped by a future rebuild would be a silent
regression, and a count would not catch it. The sweep is **throttled in the
database** to about hourly (`private.retention_sweep_is_due()` — LIVE runs
only since fix round 1: the throttle used to read every run, so the dry-run
preview button postponed the live sweep it was previewing) rather than
given a cron entry of its own: the other four halves are latency-sensitive and
this one is not, and "there is one clock" is worth more than a cheaper
predicate.

**Every period lives in ONE declared place**, `private.retention_periods()` —
eleven classes, each with its interval, what it applies to, the column its
clock runs from and the authority that set it. Counsel's answer to Q133 is a
reissue of that one function. It is a FUNCTION and not a settings table on
purpose: these numbers are a legal position stated on a published page, and a
row anybody can UPDATE is a legal position that can change with no diff, no
review and no record. `private.organisation_retention_days()` and
`private.feedback_retention_cutoff()` — the two read-time expiry paths that
predate it — were rebuilt to derive their numbers from it.

**A table nobody has decided a retention answer for stops the job.**
`private.retention_subjects()` classifies every table in `public` as swept
under a named class, cascading with its parent, retained with its workspace,
platform reference data or never purged; `private.assert_retention_roll()`
derives the same list from `pg_class` — **since fix round 1 before a run is
opened, before the object manifest names a key, AND at step 0 (see "What the
review found" below), and over materialized views and the `private` schema
as well as tables in `public`** — and refuses an
unclassified table, a roll entry naming a table that does not exist, a table
classified twice, or a `swept` entry whose class is not declared. It earned
its keep on its first day, refusing because the task's own two new tables were
not on it.

**Eight sweeps:** stale rate-limit counters (Q110), expired feedback and its
screenshots (Q120), resolved incident alerts and their `details` JSON (Q117 —
an OPEN alert is never purged at any age, because an unresolved alert is an
outstanding problem and deleting it would delete the reason nobody has looked
at it), failed erasure jobs at 90 days (Q175 — a SUCCEEDED one is kept for
ever, because both its user columns are already null and it is the proof a
statutory deletion happened), jobs stuck `running` (Q166 — FAILED, not
deleted: what is released is the one-live-job index that was locking somebody
out of a statutory right), document bytes (Q52), the audit purge above, and
the 60-day workspace purge (Q88/Q92/Q102), which CALLS
`private.erase_organisation()` rather than reimplementing it and is the first
caller that primitive has ever had.

**Storage is the half that cannot be transactional, and both directions are
handled.** `public.retention_object_manifest(p_run_id, p_limit)` derives every object key in
the DATABASE — the runner deletes what Postgres named and can name nothing
itself, the erasure runner's rule, **and since fix round 1 Postgres names
nothing at all for a run that would refuse** — and the runner deletes bytes BEFORE the
rows, because the feedback sweep and the workspace purge both refuse to remove
a row whose object is still stored. If a run dies in between, the residue is
bytes gone and rows not, which is the direction of "the data is deleted" and
never of "the data is exposed", and the next run finishes the job from the
object's ABSENCE (`documents.bytes_purged_at` is derived, not bookkept). The
other direction — an object no row names — is the manifest's orphan half.

**Nothing is deleted silently.** One correlation thread per run plus one
summary audit row (`retention.swept`, counts and never content, actor = the
Q130 tombstone, because a scheduled job has nobody on it and
`private.log_audit_event()` requires an `auth.uid()`). A DRY run writes one
too, marked `"mode": "dry"`. Every run — including a refused one — writes a
row to `public.retention_runs` with what it swept, how long it took and what
it REFUSED, and `/super/health` renders the last five: "the audit purge has
refused its ceiling on every run for a month" is exactly what an operator
needs to see, and a warning in the Postgres log on a hosted database is not
visible from anywhere. **Since fix round 1 it is also an incident alert**
(`retention_run_refused`, below), because a column on a page is visible only
to somebody who looks.

**C2 — step 0 ran after the bytes were gone.** The runner read the manifest,
DELETED THE OBJECTS and only then called `run_retention_sweep()`, where the
roll was asserted: the reviewer measured a run recorded `failed` whose file
had already been destroyed. The fix (`20261004002000`) is in the database
rather than in the order of three TypeScript lines: **`start_retention_run()`

per bucket, so a refusal condition that ARRIVES between the two — an
unclassified table created, a client grant added to a clock — is not seen
until step 0, by which time the named objects are gone and the run is

locally, `lib/retention/runner.ts` from `readManifest` to `removeObjects`),
it takes a concurrent DDL to hit, and every object named was legitimately
expired at the instant it was named. It is the inherent residual of
bytes-first, not a defect the gates cover, and no code change closes it
short of a two-phase delete nobody can have.

**One run at a time** (`20261004003000`, I2). Two starts used to give two

`supabase/tests/retention_concurrency_probe.sh` drives it with two real

the product writes is derived from the live catalogue and planted either side

#### When a retention run refuses

A LIVE run that refuses or fails files ONE `retention_run_refused` incident
alert per distinct (sweep, reason) — a trigger on `public.retention_runs`, so
every writer of a refusal passes it; codes and counts, never content — and
the existing digest emails it. A later live run that completes without
repeating the fault resolves it as the system (`retention_run_recovered`), so
**an alert that is still open is a fault that is still happening.** It is NOT
filed for `retention_disabled` (a switch somebody chose, already audited with
its reason) or `retention_run_in_progress` (an overlap), nor for a preview.
What the operator does next, by reason:

| reason | what it means | what to do |
|---|---|---|
| `unclassified_retention_subject` | a migration added a table or materialized view to `public`/`private` that `private.retention_subjects()` does not classify. **Nothing is being deleted at all** until it is | decide its retention answer and reissue the roll in a migration. This is the job working |
| `undeclared_retention_clock` / `forgeable_retention_clock` | a sweep reads a timestamp column nobody classified, or a client role can write a clock with no guard | classify it in `private.retention_clock_columns()`; if it is client-writable, guard it FIRST. Do not add a guard name that does not exist — the assertion checks |
| `audit_purge_over_ceiling` | more than a fifth of the audit log, and more than 1,000 rows, are past the period. Either the clock/period/column is wrong, or the job was off for a long time and this is a genuine backlog. **The ceiling cannot drain itself** — each run deletes at most 500 and the ceiling judges every candidate — so it refuses every hour until a person acts | the alert's `details` carry both row counts. If it is a wrong clock, fix that. If it is a genuine backlog, release the ceiling from `/super/health` (step-up, a reason, 3 days, Q184 — built in Phase 8 Task 9a); the hard floor and the 500-row per-run limit still hold, and the release lapses by itself. A backlog larger than 36,000 rows needs a second release after the first expires |
| `audit_retention_below_floor` | `private.retention_periods()` declares an audit period under one year | it is refusing to delete a year of evidence. Correct the declaration |
| `run_abandoned` | a run crashed and was reaped past the `stuck_job` period | read the runner's logs for that run id; the next run has already started normally |
| `storage_remove_failed` / `manifest_unreadable` | Storage or the manifest faulted; rows were NOT swept, which is the safe direction | check Storage; the next run retries the identical set |
| `unknown` | the runner recorded a reason that is not a code | read the runner's logs for that run id |

**A fourth Vault pair and a fourth bearer secret** (`retention_runner_url` /
`retention_runner_secret`, § 15), separate from the digest's, the export
runner's and the erasure runner's. The argument for separation is at its

still cannot choose what to delete — every period is declared in the database

### Data subject requests (Phase 8 Task 3)

**Intake is a signed-in session and nothing else, and that IS the identity verification.** `public.submit_data_subject_request()` takes no user argument; `private.data_subject_requests_before_insert()` stamps `user_id` and `user_email` from `auth.uid()` and refuses a sessionless write (42501), so a request cannot be filed in somebody else's name by any path — the app's form, a stripped form post or a direct PostgREST call. **There is deliberately no unauthenticated intake and no operator-filed request**: either would put identity verification in an operator's hands with no evidence trail. A person with no account, or who cannot sign in, is told on `/legal/data-subject-rights` (**v3** since this task's fix round) to email `SUPPORT_CONTACT_EMAIL`; that is handled as correspondence outside these tables.

**The operator's identity check for an emailed request, written down (review finding M5).** It was owed as soon as the page invited the email, not when a later task formalises it, and it is published on `/legal/data-subject-rights` in the same words, because a procedure the person cannot read is one they cannot hold us to. Follow the ICO's position: ask only what is necessary and proportionate, disclose nothing until satisfied, and start the clock when identity is settled (UK GDPR Art 12(6)).

1. **Reply to the address the request came from.** Ask which email address or addresses we would hold them under, and enough about the records to find them (for a `workspace_records` request, the business whose workspace they are in).
2. **Disclose nothing first.** Do not confirm or deny that an account, a contact record or a workspace exists until step 3 is satisfied — the reply to an unverified stranger must be identical whether or not we hold anything.
3. **Prefer a check that uses what we already hold.** A reply from an address already on an account, or confirmation of details already in the record. Do **not** ask for a copy of an identity document unless nothing less will do; if it is asked for, ask for only the parts needed, and keep no copy after the request is answered (a scan of a passport retained in a mailbox is a new, worse processing problem than the one being solved).
4. **Escalate only on real doubt**, and tell the person the day the month starts running from — which is the day the identifying information arrives, not the day the first email did.
5. **Record what was checked and when** with the request, and if identity cannot be established, refuse **in writing**, say why, and say that the ICO can be complained to about that decision.

**An emailed request has no row, and therefore no clock the database watches (Q161).** Every write path into `public.data_subject_requests` stamps the requester from the session and takes no user argument — which is exactly what makes a request unforgeable, and also means the operator cannot file one on somebody else's behalf. So an email request lives in the support mailbox alone: no `due_by`, no `dsr_deadline_approaching`, no `dsr_overdue`, and nothing on `/super/data-requests`. The 30-day obligation is identical for both routes and the machinery that watches the clock covers one of them. **Do not close this by letting an operator name a requester**; the shapes worth considering are a register row against a verified-email subject with no account, or an intake that creates the account. Q161.

**The controller/processor split is a column, not a convention (Q132).** `subject_scope` is `account` (GetSetPaid is the controller; we answer it) or `workspace_records` (a customer workspace is the controller; we ROUTE it and record which workspace and when). The workspace is named by the OPERATOR when routing, never by the requester — a person who is a contact in a promoter's workspace is normally not a member of it — which also removes the question of whether a requester may name a workspace they have no relationship with. Counsel still confirms the characterisation; the page carries that gap.

**Operator notes are a SEPARATE TABLE, because RLS filters rows and not columns (Q103).** `public.data_subject_request_notes` has one policy — the aal2 platform superuser's SELECT — and no own-rows policy at all, so there is nothing for the requester to read rather than something a page chooses not to render. The psql suite's § DN and the permission matrix both assert that the principal who CAN read the request reads zero of its notes.

**No free text reaches the audit log.** `detail` and `rejection_reason` are untrusted input and `audit_events` is superuser-readable across every tenant, so the payloads carry the right, the scope, both states, the deadline, whether a closing transition was inside the 30 days, and the LENGTH of the text — never the text. Same rule for a note's body, and for the deadline alerts' `summary`/`details`.

**A rejection reason is shown back to the requester, and the operator's field says so** — the Q103 precedent from `organisations.lifecycle_reason`. Refusing a request is the one action on `/super/data-requests` behind step-up; progressing, routing and noting are ordinary casework, and a prompt on every one of them is a prompt people learn to click through.

**The Task 4/5 seam exists and its constraint is written but dormant.** `fulfilment_kind` / `fulfilment_reference` / `fulfilment_recorded_at` are writable only from a session with no person on it — a server-side job — and never by a client. **That sentence used to read "from a path where row security is not active", and it was false** (review finding I1): the guard tested `row_security_active()` inside a `SECURITY DEFINER` trigger owned by `postgres`, where the current user IS the owner, so it answered `false` for every caller and the branch could never raise. The only thing between a client and the seam was the absent `UPDATE` grant, and the assertion meant to prove the guard was answered by that missing grant — deleting the guard outright left the suite at 113/0. Since `20260925000000` the guard decides on the **session**, which `SECURITY DEFINER` does not change: a seam write is refused (42501, hint `fulfilment_seam_is_server_only`) when `auth.uid()` is not null or the session's `role` setting is `authenticated`/`anon`, and the refusal carries its own hint so a held guard and a missing grant are distinguishable. `private.data_subject_requests_before_update()` refuses marking an account-scope access, portability or erasure request `fulfilled` without the seam — gated on `private.dsr_fulfilment_job_ready(kind)`, **one predicate per job since the same migration** (one boolean for both would have made every account ERASURE request unfulfillable between Task 4 shipping and Task 5). A seam-only write now moves only the seam, only on an open request, and only for a right whose `fulfilment_kind` matches. The psql suite flips the predicate inside a rolled-back transaction, so the rule is measured now rather than trusted later.

### Browser storage and consent (Phase 8 Task 2)

**No cookie banner ships (Q129), because every item of browser storage the product sets is strictly necessary** — the Supabase session cookie, `gsp_current_org`, the idle-timeout key and `gsp:sidebar-pinned` — and PECR exempts those. That statement is kept true by three checks, not by this paragraph:

- `tests/unit/legal/storage-census.test.ts` (in CI) parses **every app-shipped script file** with the TypeScript compiler — the set is derived (everything outside `node_modules`, `.next`, the root dot-directories, `tests/`, `supabase/`, `scripts/`), so a root `instrumentation-client.ts` or a new folder is scanned the day it exists, and a test fails if an app module imports from a skipped folder. It finds: a `.set(` on any cookie store — next/headers' `cookies()` under any local name, including `(await cookies()).set(...)`, a `.cookies` member, the Cookie Store API, and any alias of those — and a store that escapes (passed on, returned, destructured for a write); an assignment to any `cookie` member; any constant string, however concatenated, containing `set-cookie`; the Supabase clients; `localStorage`/`sessionStorage` writes however the store is reached (`?.`, brackets, constant-built names, aliases) and their escapes; IndexedDB, Cache Storage, service workers and `navigator.storage`; `next/script`/`@next/third-parties`, loading elements (`<script>`, `<iframe>`, `<object>`, an absolute or computed `<link href>`, any absolute `src`/`poster`/`data`), `createElement` of a loading tag, `src`/`innerHTML` assignment, `document.write`, `eval`, `Function` **with or without `new`** (and either taken as a value), a `setTimeout`/`setInterval` whose first argument is not a function written in that file, beacons, `window.open`, and fetch/XHR/WebSocket/dynamic `import()` to a constant absolute URL; and tracker globals and hosts. **Since the scoped re-review (N1)** it also follows a `cookies` RE-EXPORTED by another scanned module (`export { cookies as jar } from "next/headers"`, `export *`, a barrel of a barrel, a namespace import of one) — a cross-module pass over the whole set, because the per-file scan could not see that shape at all; a destructuring or `for…of` assignment target (`[document.cookie] = [v]`, `for (localStorage.k of xs)`); `Object.assign`/`Object.defineProperty`/`Reflect.set` onto `document` or naming a `cookie` property; and a HEADER NAME that is not a constant (`res.headers.set(built, v)`, `new Headers([[built, v]])`, a computed `headers:` key), because a name assembled at runtime can be `Set-Cookie` — the middleware's own header-copy loop is declared for exactly that reason. Each site must be declared against an item of `lib/legal/storage-inventory.ts` — the list the public Cookie Policy renders — or, for the four server-side sites (three service-role Supabase clients and the Brevo call), declared as setting nothing, in a module that must import `server-only`. It also requires every runtime dependency to be declared with what it stores, forbids static HTML/JS under `public/`, and requires the CSP to **name** no third-party script, image or frame host. **That CSP check is not a block**: `script-src` carries `'strict-dynamic'`, under which a script the page already trusts may insert a script from any host, and a first-party cookie such a script writes (`_ga`) is governed by no CSP directive — so it is the source scan, not the CSP, that stops trusted code loading a tracker (whether `'strict-dynamic'` should stay is Q155). The first cut (regex over five named folders) missed `(await cookies()).set(...)`, aliases, `?.`, bracketed globals, anything after a `//` inside a string, and every root file (review finding I1); the thirteen the review measured and forty-two neighbours (55) are now fixtures run on every CI build. Measured on the real tree: a new `localStorage` key is 3 red tests, a `next/script` loader 1, an undeclared dependency 1, and the review's evasions dropped into `instrumentation-client.ts`, `hooks/` and `components/` are named one by one. Two further checks stand where a build would: **every scanned file must PARSE with no syntax errors** (N5 — `ts.createSourceFile` never throws, so a broken file was scanned with recovery and could hide the statement that broke it), and the four server-side sites' `import "server-only"` is read **from the parse, not matched with a regex** (N6 — a regex accepts the same line inside a block comment), with a reachability walk proving no `"use client"` module reaches one of those four through any chain of repo imports, stopping at `"use server"` modules because those are an RPC boundary. `server-only` itself is enforced when **Next compiles** (`next dev` / `next build`), and CI runs neither — that walk is what stands in for it here. **It cannot see** what a dependency does at runtime, a key built from data, a store reached through a value the file did not create (a parameter), or anything injected outside the repository;
- `tests/e2e/storage-census.spec.ts` therefore reads what a real browser holds after a signed-in walk — every cookie for **every** domain (a third-party cookie is on neither the app's nor the API's), every `localStorage`/`sessionStorage` key, IndexedDB database, Cache Storage entry and service worker — asserts the four declared items are PRESENT first, then that everything present matches an inventory pattern **of the same kind**, that the browser context (page, popups and workers) contacted no host but the app and its Supabase API, and that no Content-Security-Policy violation names a third-party host (a second layer: a probe proves the listener hears a blocked load; measured, Chromium also reports that blocked image as a request, so the host check sees it too). Since fix round 1 the one excused item, Next's development-only `__next_debug_channel` database, is checked against Next's client code (where it is opened) rather than its server runtimes. **It cannot see** code paths the walk does not reach, storage only a production build or the host sets (it runs `next dev`, Q153), and **it does not run in CI**;
- `tests/unit/consent/marketing-sender-census.test.ts` requires any module that imports the email sender, other than the three transactional senders, to call `assertMarketingConsent()` (`lib/consent/marketing.ts`, over `public.consent_is_granted()`, executable by `service_role` alone).

**The day an analytics (or any non-essential) vendor is chosen, four things ship in the same change, or the censuses stay red:** (1) consent BEFORE the script or storage loads — a `consent_purposes()` row in the `analytics` category and the check at the loader, so nothing is set for a person who has not agreed; (2) a banner offering accept and reject with equal prominence, plus a withdraw control on `/account/privacy` (withdrawal as easy as giving); (3) the inventory entry, which republishes the Cookie Policy table (and, if its prose changes, a new unreviewed Cookie Policy version); (4) the vendor in `docs/sub-processors.md` and `lib/legal/sub-processors.ts` together (the drift test binds them), with its transfer basis. A CSP change to allow the vendor's host is part of (1), not a separate decision.

**The consent ledger itself** (`public.consents`, `20260923000000`) is append-only for every role (`postgres` included), attributed from the session by a `BEFORE INSERT` trigger every writer passes, and holds no IP address and no user agent (Q149). `policy_version` is a real foreign key to the immutable published legal document; a grant must name the version currently published **and the exact wording shown, from the database's own list** (`private.consent_statements()`, `20260923003000` — before fix round 1 any well-formed token, or none, was stored). A grant can be withdrawn **once**: `withdraws_id` is unique (`20260923004000`), because the trigger's alternation rule alone let two REPEATABLE READ withdrawals commit against one grant. No client role holds a write privilege; `record_consent()` takes no user argument. The aal2 platform superuser reads every row for oversight. **A row can be deleted only by the `ON DELETE CASCADE` from its own auth account** — since `20260923002000` the guard checks that the account is actually gone, where it used to trust any DELETE issued by a trigger (a trigger on any table could empty the ledger). **And in practice no row is deleted at all today:** every consent event writes an `audit_events` row whose `actor_user_id` references `auth.users` with no `ON DELETE` action, so the account of anyone who has ever consented cannot be deleted (23503) — the cascade is reachable only after those audit rows are removed, which is Task 5's erasure design (Q130), and whether the consent history should survive erasure is Q148. `rls_phase8_consents.sql` (143 assertions) and the runner's HTTP block and REPEATABLE READ withdrawal race measure it; the permission matrix registers the RPC and the table.

### The platform superuser grant

`public.platform_admins` is the platform-superuser allowlist. It has RLS enabled with **zero policies and zero client grants**, so no client role — not even a leaked service-role key — can write to it. Rows are added by migration or DBA action only, and it seeds **empty** on purpose.

That is the correct shape for the table and a launch blocker for the product, because three separately-correct decisions compose into a dead end while it stays empty:

- `audit_events`' only SELECT policy is `has_platform_permission('view_audit_log')`. **With an empty allowlist the audit trail is write-only** — it is being recorded correctly and cannot be read by anyone, through any path the application offers.
- **Corrected 2026-09-08 (Phase 7 Task A) — the premise changed.** `organisation_subscriptions`' write policies are still superuser-only, but `create_organisation()` now writes a Starter row for every new organisation at birth (`20260908000000`), and every organisation that predates that migration was backfilled one — so an empty `platform_admins` no longer strands every organisation on Free. The dead end that remains is narrower: **no organisation can ever be moved off Starter** (upgraded to Pro, comped, or otherwise billing-overridden) with an empty allowlist, because `organisation_subscriptions_update_platform_billing` is the only write path and it is superuser-gated. Starter carries `crmWrites: true`, so this is a growth/upsell dead end, not a "every write in the product refuses" one — still worth fixing before launch, but not the same severity this row used to claim.
- The Platform-Superuser branch of the MFA gate and `public.is_platform_admin()` are dead code until a row exists.

`supabase/migrations/20260827210500_seed_platform_superuser.sql` grants it to the founder. Two things about it need checking after deploy, which is why it is on this list rather than assumed done:

1. **It looks the user up by email, and is a no-op if that account does not exist yet.** No Supabase auth user id existed when it was written, so it could not hardcode a UUID. If the migration is applied before the founder has signed up, the allowlist stays empty and the migration must be re-run afterwards. It is idempotent (`on conflict do nothing`), so re-running is safe.
2. **Verify the row actually landed**, rather than assuming the migration did it:
   ```sql
   select u.email from public.platform_admins pa join auth.users u on u.id = pa.user_id;
   ```
   An empty result means the product is in the dead-end state described above.

Granting or revoking further superusers is documented in that migration's header. Note that allowlist membership is necessary but **not sufficient**: per § 4 and `20260827210000_mfa_aal_permission_gate.sql`, every platform permission also requires an `aal2` session, so the founder must enrol TOTP before any superuser-gated policy will pass.

### Response security headers

Set in code, not config, so they ship with the app rather than needing a hosted-dashboard step — listed here so a launch review can confirm them rather than assume them. `lib/security/headers.ts` is the single definition; `next.config.ts` applies the static ones and `proxy.ts` applies the nonce-bearing CSP.

Two of them are **deliberately conditional on `NEXT_PUBLIC_SITE_URL` being `https:`**, and therefore are NOT present in local development:

- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
- `upgrade-insecure-requests` in the CSP

So confirm on the deployed environment, by reading actual response headers (`curl -sSI https://<host>/login`), that both appear. If `NEXT_PUBLIC_SITE_URL` is misconfigured to `http://` in production, the app will work and will silently ship without HSTS.
