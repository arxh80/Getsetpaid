# SECURITY.md

Internal engineering reference **and** pentest/audit prep document for GetSetPaid. Consolidates security decisions already made across `CLAUDE.md` and the PRD (`getsetpaid_crm_prd.docx` §10, §18) into one place, plus defines rate limits, incident response and vulnerability disclosure that didn't exist anywhere yet.

This is not the public-facing Trust Centre page (PRD §12) — it is written for engineers and external security testers, not customers. Nothing here is a substitute for the pre-launch independent penetration test (PRD §10.8) or legal/privacy counsel review (see `CLAUDE.md` § Legal and regulatory compliance).

## 1. Principles

- No feature is production-ready until threat modelling, access-control tests and OWASP-aligned tests pass — security is an acceptance criterion, not hardening applied after the fact.
- Least privilege everywhere: roles, database roles, service accounts, superuser access.
- Private by default: tenant data never crosses into the network/public surface without an explicit, tested, opt-in policy.

## 2. Tenancy and Row Level Security

- RLS is enabled on every tenant-owned table before the application can reach it. Separate policies per operation (SELECT/INSERT/UPDATE/DELETE) where useful.
- Access is derived from the authenticated session and organisation membership, checked **in the database** — never from a client-supplied organisation ID.
- **Network tables, as built (Phase 6) — the base table is deliberately readable and the VIEW is the masking control, not the policy.** `network_profiles_select_published_directory` (`20260904003000`) is **the one policy in the whole schema that permits a cross-tenant read**, and its own comment says why: a row policy filters rows, it cannot filter columns, so a caller who queried `public.network_profiles` directly would see `organisation_id`, `entity_id` and every value column, including ones the publisher marked `hidden`. **Two views are the only sanctioned read path into another organisation's published data**: `public.network_directory` (`network`-level fields only) and `public.network_connected_profiles` (`network` + `connections`-level fields, for an organisation on either side of an accepted `network_connection_requests` row — Q80's org-to-org symmetry). Both carry `security_invoker = true`, so row reachability is still the caller's own `network_profiles` policy above — one gate, not two that can drift — and both are structurally pinned to a fixed dependency set (**the N2 invariant**): `network_directory` to exactly `{public.network_profiles}`, `network_connected_profiles` to exactly `{public.network_profiles, public.network_connection_requests}`, nothing else, ever. Asserted from `pg_depend`, not promised in a comment, by `supabase/tests/rls_phase6_network.sql` § ND, with a non-vacuity control (`public.event_finance_summary` must independently resolve to `{financial_entries}`, proving the query can see dependencies at all) — the failure mode this catches is a future edit joining a private table into either view to resolve a nicer display name. A field the publisher marks `hidden` is additionally stored as **NULL** in the base column (`network_profiles_hidden_fields_are_null`, N3), so the view's mask is the second of two controls, not the only one. Application code must never select from `public.network_profiles` for a foreign organisation — `lib/network/discovery-list.ts` and `lib/network/discovery.ts` name the two views as their only tables, and `tests/unit/network/no-private-table-in-network-path.test.ts` is the source-only, CI-visible census that a future edit cannot grow a shortcut around them invisibly. `network_links` carries only ordinary tenant-scoped policies — no cross-tenant SELECT at all (Q82: "the profile's owner is never told" who linked it). `network_connection_requests` is narrower than "tenant-scoped" but not zero: `network_connection_requests_select_view_network` is a disjunction over `from_organisation_id` OR `to_organisation_id`, so **either party to a request reads that request's row** — a recipient organisation reads a row another tenant inserted, learning that tenant's `from_organisation_id` and `from_network_profile_id`. That is the point of a two-party record (the recipient must see who is asking, Q78), and it is the table `network_connected_profiles` resolves the accept unlock against — a tester should look at it, not be told there is nothing there. So `network_profiles_select_published_directory` is the only *unilateral* cross-tenant read among the three tables — the only policy through which an organisation reads another tenant's row without being a named party to it — and it is written so that fact "is impossible to miss" (its own comment, verbatim). Regression tests: `supabase/tests/rls_phase6_network.sql` (§ ND the dependency assertion, § NG the `anon`-grant census across all five objects — three tables, two views) and `supabase/tests/network_leakage_phase6.sql` (the consolidated adversarial proof, every tenant-private table, query path by query path). See § 10's "Network privacy leakage" row for the residuals this does not close.
- Finance and audit tables carry additional, more restrictive policies than general CRM data. **`public.financial_entries` (Phase 5) is the most restricted surface in the product, and the shape is deliberate.** It has **three** policies and no fourth: SELECT, INSERT, UPDATE, and **no DELETE grant at all** — a financial record is soft-deleted (7-year retention, § 8) and never hard-deleted, so the DELETE policy that does not exist is the control. Two new permission keys carry it, `view_finance` and `manage_finance` (`20260903002000`), held by Owner, Admin and Finance only; `role_requires_mfa('finance')` was already true, so both keys are simply not held below `aal2` and the MFA gate needed no new code. **Reads are NOT entitlement-gated and that is a decision, not an omission** (founder Q67): the SELECT policy names `private.permitted_organisations('view_finance')` and nothing else — no `finance_module` term — so an organisation that downgrades from Pro keeps reading its own finance history, matching "downgrading must never silently delete data" (`CLAUDE.md` § Permissions). The **write** policies additionally name `private.finance_module_organisations()` (Pro only), and the tier conjunct sits in `WITH CHECK` only, deliberately **not** in the UPDATE's `USING`, so a downgraded write refuses with a loud `42501` rather than PostgREST's `204`, which is indistinguishable from success. The same split reaches the finance **custom-field value** path: `private.entity_is_manageable`'s `financial_entry` arm carries the `finance_module` term (`20260903030000`) and `entity_is_visible`'s does not. `public.event_finance_summary` is a `security_invoker` **view**, so its base read runs under the caller's own SELECT policy rather than the view owner's — a caller without `view_finance` gets no row, not a zeroed one. Regression tests: `supabase/tests/rls_phase5_finance.sql` (§ FB shape, § FD the six non-finance roles, § FE the tier gate, § FF the aal1/aal2 inversion, § FI the custom-field value path including the downgrade case) and the "Phase 5 finance at the API surface" HTTP block, which elevates a real session with a real TOTP enrolment.
- **Break-glass impersonation, as built (Phase 7 Task 2) — the ONE place a non-member reads a tenant, and the grant is derived, not minted.** `CLAUDE.md` § Superuser dashboard makes this the only sanctioned deep-access path in the product ("No direct tenant-data access outside impersonation"), so its shape matters more than any other single control. `public.impersonation_sessions` (`20260908020000`) has **two SELECT policies and no write policy of any kind**, and `authenticated` holds `SELECT` on it and nothing else — every transition goes through one of five `SECURITY DEFINER` RPCs (`request_impersonation`, `accept_impersonation_request`, `decline_impersonation_request`, `start_impersonation_session`, `end_impersonation_session`), each carrying its own authorisation guard **and its own audit write in the same transaction**. **No synthetic membership row is ever created**: the grant is `private.impersonated_organisations(permission)`, which returns the target organisation only while (a) a row for this caller is `status = 'active'`, (b) `expires_at > now()` — evaluated on **every** permission check, so expiry is immediate and needs no sweep job, (c) the caller still passes `private.has_platform_permission()` (still allowlisted, still `aal2` — de-allowlisting or dropping to `aal1` kills a live session with no row to update), and (d) the permission is one `public.role_permissions` grants the **`read_only`** role, joined rather than hardcoded so the envelope cannot drift from the product's own definition of Read Only (Q96). That one helper is wired into **all three** permission consumers — `public.has_permission()`, `private.permitted_organisations()` and `private.full_scope_organisations()` (record scope, Q97, or every list would render empty) — so the rule cannot be half-applied; `rls_phase2_crm.sql` § M1d2's parsed-body census asserts the disjunct is present in **both** mirrored bodies, and `rls_phase7_impersonation.sql` § IM re-runs the whole M1 sweep **with a session live**, which § M cannot (none exists when it runs). **Consent is the gate and is not the operator's to give**: `accept_impersonation_request` requires `manage_organisation` **in the target organisation** (Owner/Admin, both MFA-required), the accept surface lives inside the customer's own workspace, and the superuser cannot reach it *even while impersonating* because `manage_organisation` is not in the read-only envelope — support access cannot extend itself. Either party may end a live session. Regression tests: `supabase/tests/rls_phase7_impersonation.sql` (108 assertions — § IP the standing catalogue guard that `read_only` holds no `manage_`/`merge_` key, § IR the table's RLS and the absence of any client write path, § IG the four-stage lifecycle including the aal1 case, § IW writes refused policy by policy, § IX the one-organisation scope boundary, § IE the time-box measured with the `status` column still reading `active`, § IS the suspension consequence, § IA the audit trail) and `tests/integration/rls/impersonation-matches-db.test.ts` (the TypeScript↔SQL binding). See § 10 for the residuals.
- **Billing/feature override tables, as built (Phase 7 Task 4) — RPC-only writes, one deliberately cross-tenant read, and reason columns every member of the target org can read.** `public.organisation_billing_overrides` and `public.organisation_feature_overrides` (`20260909000000`) are writable by no client role except through the four audited RPCs (`grant_billing_override` / `revoke_billing_override` / `grant_feature_override` / `revoke_feature_override`, `SECURITY INVOKER` so the policies are the enforcement, with `private.log_override_event()` as the `SECURITY DEFINER` audit bridge): the INSERT/UPDATE policies require `private.has_platform_permission()` **and** a transaction-scoped marker (`private.override_transition_in_progress()`, its own GUC `app.override_transition`) that only the RPCs set — so a raw PostgREST POST/PATCH from the superuser's own browser matches nothing — and a policy-independent `BEFORE INSERT OR UPDATE` trigger (`private.override_table_guard()`) refuses the same writes without consulting any policy. That is Task 3's two-gate shape, reused here as declared defense in depth: both tables are brand-new, so unlike Task 3 there is no pre-existing looser policy for Gate 2 to be shown closing. **No DELETE policy exists for any client role** — revocation is a column write and history is never removed. Two SELECT policies each: `*_select_member` gives **any active member** of the org the full row — structurally required, because `lib/entitlements/policy.ts`'s `getOrganisationEntitlements()` resolves entitlements under the caller's own RLS for every role, and an admin-only policy would make overrides silently not apply to non-admin sessions — which means `reason` and `revoked_reason` are member-readable through PostgREST, on revoked/expired history rows too (RLS filters rows, not columns; the Q103 pattern), and all four operator reason fields warn about exactly that in the field hint; and `*_select_platform`, scoped to the platform superuser at `aal2`, which the `/super/billing` list and the revoke UPDATE's row-matching need — aggregate metadata only (org, tier/seats/flag, reason, clocks), no record content. **Effective-tier resolution is a single point per language**: `private.effective_organisation_plan()` (`SECURITY DEFINER`) is what all four SQL tier gates (`crm_write_organisations`, `custom_field_limit`, `finance_module_organisations`, `network_publish_organisations`) read, and `getOrganisationEntitlements()` is the TypeScript twin. Only an override that **names a tier** bypasses the subscription's own status — corrected by `20260909010000` after review finding I1 caught the first cut extending that bypass to seats-only overrides, silently reviving a cancelled subscription's paid-tier writes in SQL while TypeScript resolved Free. Auto-revert is read-time expiry: `private.active_billing_override()` / `private.active_feature_override()` stop returning the row at `expires_at`, with nothing scheduled and the row kept as history. Regression tests: `supabase/tests/rls_phase7_overrides.sql` (51 assertions — grant/expiry/revoke both sides of the boundary, RPC-only writes attacked as the org's own Owner and as the superuser's raw PATCH, foreign-admin-reads-zero, downgrade-deletes-nothing, audit trail) and `tests/integration/entitlements/billing-override-matches-db.test.ts` (the TypeScript↔SQL binding, including seats-only + cancelled).
- **The permission-test gate (Phase 7 Task 7) — one suite that proves every operator surface refuses every wrong principal, with a positive control beside each refusal.** `CLAUDE.md` § Permissions is the bar: "an action is allowed only if ALL of these permit it ... entitlements are enforced server-side — hiding UI is not enforcement." Two files carry it. **`tests/integration/security/phase7-permission-matrix.test.ts`** (222 assertions) covers the RPC, table and grant layers over PostgREST with the anon key and a real principal's JWT — the request a script sends, never the form. **`tests/e2e/super-permissions.spec.ts`** (12 tests) covers the page layer with real HTTP GETs through the app's own sign-in form, plus the one `/super` route handler and a search of every script the browser actually loads. **The inventories are MECHANICAL**: the thirteen platform-superuser-only RPCs, the five Phase 7 RPCs that are deliberately member-reachable, and the seven Phase 7 tables come from `pg_proc`/`pg_class` queries (reproduced verbatim in the file header), and the seven `/super` pages come from a glob of `app/(app)/super/**/page.tsx` — both re-run **at test time**, so a Phase 8 grant or page that nothing probes lands as a red test naming itself rather than as a silent gap. **Seven principals**: anonymous, an authenticated user who belongs to no organisation, a Read Only member, an **Org Owner at aal2** (the plan's named case — Owners hold every in-tenant permission and are the likeliest accidental grantee), that Owner while a **live impersonation session** on their workspace is granted to the superuser, the Owner of a workspace carrying an **active Pro billing override** (entitlement must not leak into platform policy), and the **platform superuser one factor short of aal2** — the case Tasks 1–6 each claimed and none proved in one place. `service_role`/`postgres` are not tested as "refused" (they bypass by design); instead the suite proves neither reaches the browser, by fetching back every loaded script and the document itself and searching for the service-role key, with the **anon key found** as the control that the search is looking at anything at all. **Every refusal carries a positive control, and that is the point of the gate**: a refusal test and a "this principal could never have reached it anyway" test are indistinguishable from the outside and mean opposite things, so each refused principal calls an RPC with the same argument builder the aal2 superuser succeeds with in the same run against the same rows; every one of the seven tables is asserted NON-EMPTY through the superuser's own read before any "reads zero rows" claim about anybody else counts; every `/super` page is walked by the aal2 superuser and asserted to render its own `<h1>` and `<title>`; and the **Owner and Admin browser personas are walked onto an Owner/Admin-only surface** (`/settings/custom-fields`, `manage_custom_fields`) and the control asserted present — with a manager asserted to get the blocked sentence instead, so the negation is a statement about the key and not about a page that rendered nothing. "Refused" means the table is byte-for-byte unchanged (an md5 over the whole table, not a row count) **and** that no audit row was minted, because three of the thirteen RPCs write their audit row first on the success path. The gate was **verified red**: removing the `session_is_aal2()` term from `private.has_platform_permission()` in-session takes the matrix from 222/0 to 199/23.
- `SECURITY DEFINER` functions are used only where necessary, with `search_path` locked and `EXECUTE` restricted; every one is reviewed individually.
- Service-role/secret keys bypass RLS entirely and must never reach the browser.

## 3. Input handling

- All queries are parameterised or built with a trusted query builder — no string-concatenated SQL, anywhere.
- Search/filter/sort inputs map to an allowlist of column names and operators; free-form input never becomes a column/operator name.
- Rich text is sanitised against stored and reflected XSS. URLs are validated against an allowlist of protocols (`javascript:` and `data:` rejected). `dangerouslySetInnerHTML` is avoided; where unavoidable, it requires security review.
- A strong Content Security Policy is shipped with the Next.js app.


**`public.events.ticket_link` is guarded three times, and the middle one is stronger than its own comment claims (measured, Phase 3 Task 8).** `normaliseWebsite()` refuses a non-http(s) scheme on the way in, `safeHref()` refuses it on the way out (a value it rejects renders as inert text, never as an anchor), and the column additionally carries `events_ticket_link_is_http`, `check (ticket_link is null or ticket_link ~* '^https?://')`. That CHECK's own comment (`supabase/migrations/20260901000000_events_and_lineup.sql:147`) calls itself "DEFENCE IN DEPTH, NOT THE CONTROL"; the phrase "a row written before it, by an import, or by a direct PostgREST PATCH is still possible" is the DETAIL PAGE's comment (`app/(app)/[orgSlug]/events/[eventId]/page.tsx:60-64`), not the constraint's — and on this column none of the three is possible today: it is a **validated** CHECK (not `NOT VALID`), so it binds every writer including `postgres` and `supabase_admin`, and `public.events` was created *with* it, so there are no older rows. Phase 3 Task 8 tried to plant a `javascript:` ticket link as `postgres` for a render test and could not. **Two things follow.** A pentester should not spend time hunting for a stored `javascript:` on this column — but `contacts.website` and `contacts.socials` have **no** equivalent CHECK and a hostile value *is* plantable there, which is why `tests/e2e/tenant-breakout.spec.ts` plants one and asserts the render. And nobody should weaken `safeHref()` on the strength of the CHECK: it is one column's constraint, it does not run on render, and it does not normalise.

## 4. Authentication and session security

- Identity: Supabase Auth. Email/password and magic-link/OTP at MVP; **Google SSO ships at MVP**, Microsoft SSO is post-MVP.
- Session limits: **30-minute inactivity timeout, 12-hour absolute session lifetime.**
- MFA is **required** for Platform Superuser, Organisation Owner, Admin and Finance roles. Optional (not enforced) for all other roles at MVP.
- MFA is **enforced at every sign-in, not just at enrollment**. A privileged user with a verified TOTP factor who signs in at `aal1` is challenged for a code before reaching the app — an enrolled-but-never-challenged factor satisfies the requirement in name only. Founder decision, 2026-08-27.
- **MFA recovery (lost authenticator) has no self-service path at MVP.** Because the challenge is enforced, a privileged user who loses their TOTP device cannot sign in at all. There are no backup codes and no admin reset UI. The only recovery today is a manual operator action: delete that user's row from `auth.mfa_factors` in the Supabase dashboard (SQL editor, filtered by `user_id`) after verifying the requester out-of-band, which drops them back to the enrollment gate on next sign-in. **This is a deliberate MVP gap, not an oversight** — self-service recovery (backup codes at enrollment, plus a superuser-initiated, audited reset) belongs to Phase 7 (Admin/Security) alongside the rest of the superuser dashboard. Until then: the manual deletion must be treated as a high-risk admin action — verify identity out-of-band before performing it, since it is a complete bypass of the second factor.
- **MFA is enforced in the database, not only in the UI.** `public.has_permission()` and `private.has_platform_permission()` return false for an MFA-required role on a session that has not reached `aal2` (`supabase/migrations/20260827210000_mfa_aal_permission_gate.sql`), so every write policy in the schema inherits the requirement. The app-layer gate (`lib/auth/mfa-gate.ts`, plus `assertMfaSatisfied()` on the privileged Server Actions) gives a readable refusal and stops side effects outside the database; it is not the enforcement. The anon key ships in the browser bundle by design, so anyone holding a session token can call PostgREST directly and bypass the entire Next.js app — the database is the only chokepoint on that path.

### Known limitation: MFA gates privileged WRITES, and — since Phase 2 — CRM READS

**Narrowed on 2026-08-28 (Phase 2, Task 2). The CRM tables are now `aal2`-gated for reads as well; Foundation's tables are not.** Read the whole section: the half that remains open is still the half a pentester will find.

**What changed.** Every Phase 2 CRM policy — all twelve tables, reads included — is built on `private.permitted_organisations()`, which restates `public.has_permission()`'s body including the `aal2` clause. So an Owner, Admin or Finance user on an `aal1` session now reads **zero** contacts, companies, agencies, artists, venues, rooms, links, representations, fee history, custom field definitions, custom field values and merge records. Measured over real HTTP with a real password-grant token plus the public anon key, i.e. the exact stolen-password request this section is about (`supabase/tests/run-rls-tests.sh`, "Phase 2 CRM at the API surface"), and in psql (`rls_phase2_crm.sql` § J).

**Why that is not the lockout described below.** The enrolment path needs `profiles`, `organisations` and `organisation_memberships`. It needs no CRM row. So an un-enrolled Owner still signs in, still loads the app, still reaches the enrolment screen — asserted as a lockout guard at both layers — and simply sees an empty CRM until they present a factor.

**What is still open.** A stolen `standard_user`, `booker`, `manager`, `venue_manager` or `marketing` password still reads that user's CRM rows at `aal1`, because MFA is **optional** for those roles at MVP and there is no factor to present. And Foundation's own read policies are unchanged, for the reason in the next paragraph. So the section title's original claim still holds for most of the product; it no longer holds for the largest tenant-data surface in it.

**"MFA gates CRM reads" reads stronger than it is, so state the residue explicitly.** A stolen `aal1` Owner password still yields **the organisation's entire user directory** — measured over HTTP: `profiles?select=*` returns 200 with every colleague's name and email, `organisation_memberships` returns 200 with the full role map, and only the CRM tables return zero rows. That is the enrolment-path exemption working as designed, not a second defect, but it is what an attacker actually gets and it should not be discovered during a pentest.

**Verified end to end, not assumed.** With a real TOTP factor rather than a hand-made claim set: an `aal1` password session reads `profiles`/`organisations`/`organisation_memberships`, `POST /auth/v1/factors` enrols, challenge-and-verify moves the same session to `aal2`, the CRM then reads and writes normally — and the *original* `aal1` token still returns zero rows on every CRM table. **The one thing Tasks 3-7 must not do is put a CRM query into the app shell, the MFA gate components, or `lib/auth`.** The moment a CRM read appears above `MfaEnrollGate` in `app/(app)/layout.tsx`, the un-enrolled privileged user stops being able to reach the enrolment screen and this stops being safe.

**A stolen password for a role where MFA is optional yields read access to that user's data at `aal1`.** This is a deliberate, understood boundary rather than an open defect, and it is written down here so it is found by review rather than rediscovered by a pentester.

The `aal2` requirement is attached to *permissions*, so it bites on writes. It is deliberately **not** attached to Foundation's read policies — `organisation_memberships_select_own` / `_select_same_organisation`, `profiles_select_own` / `_select_shared_organisation` and `organisations_select_member` all resolve to `auth.uid()` or `private.is_active_member()` and never call `has_permission()`. That is not an oversight: **gating those reads is precisely the lockout that would stop an un-enrolled user reaching the enrolment screen at all.** A privileged user who has never enrolled has to be able to load the app far enough to enrol, and there is no other way in. The CRM tables escape that argument only because nothing on the enrolment path reads them.

Two `SECURITY DEFINER` functions are also outside the gate, because they must be. Both are PostgREST-routable, and for both the MFA guard is app-layer only:

- `public.create_organisation()` — measured: an `aal1` session gets `200`. It cannot consult `has_permission()`, because a brand-new user holds no membership anywhere and the organisation they are creating is what makes them an Owner.
- `public.accept_invite()` — measured: a stolen-password admin invitee at `aal1` gets `204` and the membership becomes an active admin.

**Why this is not privilege escalation.** That newly-active admin's `has_permission()` is still `false` at `aal1`, so no privileged write is reachable: they cannot invite, cannot change roles, cannot rename or soft-delete the org, cannot touch entitlements or read the audit log. What the attacker gains is **read access to that org's CRM data**, which is exactly what a stolen password already granted before MFA existed.

**Why closing it is not straightforward.** Any fix has to distinguish "a session that has not presented a factor because it is on its way to enrol" from "a session that has not presented a factor because it never will", and those are the same session until the user acts. Candidate approaches, none free:

- Gate reads on `aal2` **except** the narrow set the enrolment screen needs. Workable, but the allowlist becomes a security-critical dependency of the UI: any new query on the enrolment path silently locks every privileged user out, invisibly to build, lint and type-check.
- Redirect rather than content-swap in `app/(app)/layout.tsx`. Improves the app path only and does nothing for a direct PostgREST call, which is the path that matters.
- Force the MFA challenge at the GoTrue level so no `aal1` session is ever issued to a privileged user. The cleanest answer, and not available: assurance level is per-session and Supabase issues `aal1` on password sign-in regardless of enrolled factors (measured, `tests/integration/mfa/mfa-lifecycle.test.ts`).

**Updated 2026-09-08 (Phase 7 Task 1) — the surface this paragraph forecast has now landed, and the trade-off did NOT change.** The audit log viewer (`/super/audit-log`, `lib/admin/audit-log.ts`) is the first genuinely read-sensitive cross-tenant surface in the product, and it reads `public.audit_events` through the SAME policy this whole section is about (`audit_events_select_platform_superuser`, gated on `has_platform_permission('view_audit_log')`) -- which was `aal2`-gated from the moment it shipped in Foundation, unlike the Foundation reads (`profiles`/`organisations`/`organisation_memberships`) this section's open gap actually concerns. So an `aal1` stolen-superuser-password session gets **zero** audit rows, not a widened version of the gap above: `tests/integration/rls/rls.test.ts` section D already measured this before Phase 7 existed, and the new self-audit RPC (`public.audit_superuser_audit_log_view`, section H of the same file) checks the identical `aal2` predicate before it writes anything. The forecast in this paragraph was that a read-sensitive surface landing would change the CALCULUS for whether to close the Foundation-reads gap (make the cost of leaving it open higher); having actually built one, the honest update is that it did not, because the new surface was never part of the gap in the first place -- it is aal2-gated by construction, same as every other platform-permission-gated policy since `20260827210000_mfa_aal_permission_gate.sql`. The Foundation-reads gap itself is UNCHANGED and still open; the compensating controls are still the ones in this section: the 30-minute inactivity timeout, the 12-hour session timebox, and the fact that every privileged *write* is refused. Impersonation (Phase 7 Task 2, not yet built) is the surface that could still genuinely change this calculus, since a break-glass session acting AS another organisation is a different shape of risk than a read gated the same way every other platform permission already is.

- Step-up re-authentication (re-enter credentials/MFA) is required before: changing security settings (MFA, password, email), large data exports, deleting organisation data, and any high-risk admin/superuser function — including impersonation.
- Step-up prefers MFA re-verification over password re-entry: a password re-entry returns an `aal1` session (downgrading an MFA user) and mints a new session row (restarting the 12-hour absolute clock), so it is used only where no verified factor exists. A user with neither a verified factor nor a password identity (Google SSO only, no MFA) currently cannot satisfy step-up at all and is failed closed — closing that properly needs GoTrue's `reauthenticate()` email-nonce flow, tracked for Phase 7.
- Active-session listing with remote revocation is available to every user.
- Superuser impersonation is break-glass only: the superuser requests it, the target org's admin must accept, the session is time-boxed, and the whole flow is audited (actor, org, reason, start/end). No silent or unilateral impersonation.
- **Superuser dashboard** (single hardcoded superuser account at MVP): never exposes tenant record content directly — only aggregate metadata (seat count, storage, record counts). Org suspend/delete is soft-delete only, requires step-up re-auth, and notifies the org admin. **As built (Phase 7 Task 3):** `/super/organisations`, three RPCs with a mandatory reason on every transition, one summary audit row each, a 60-day retention clock (Q88), and reinstatement in the same change — with the notification in-app only (Q45), because there is no notification subsystem at MVP. **The Connection-requests row is new, and org-scoped on purpose.** Founder ruling Q79 (2026-09-07) made a declined connection request re-requestable, which removed the one zero-cost anti-harassment control in a product with no blocking, muting or moderation; `FOLLOW-UPS.md`'s own Q79 entry names this limiter as the mitigation. Metering the DIRECTORY does not cover it — that bounds how fast an abuser can FIND organisations, not how fast they can pester ones they already found, and a request is a server action that never passes the list chokepoint. The budget binds the **organisation**, not the user: a per-user budget is bypassed by inviting a colleague (six roles hold `manage_network_connections`), and the pestered workspace experiences one workspace regardless of whose account clicked. The crossing files a `rate_limit_tripped` alert, which is the first time network harassment is visible to anyone at all. **The number is a recommended default, not a founder ruling** — changing it is one UPDATE to `rate_limit_policies` and one line here, no code.

**And it is enforced at the WRITE, not in the application, because the application-only version was bypassable.** As first shipped the only meter was a `consumeRateLimit()` call inside `sendConnectionRequestAction`, while `public.network_connection_requests` carries an `INSERT` grant for `authenticated` and a permissive `INSERT` policy — so a user who legitimately holds `manage_network_connections` in a publishing workspace, *exactly the actor this control targets*, could `POST /rest/v1/network_connection_requests` with the anon key and a session JWT, unlimited, without loading the app. No counter moved, so no alert was written either: the casual clicker was metered and the scripted harasser was invisible. **The PostgREST read-only-transaction argument that makes the directory budget app-side does not transfer to a write** — PostgREST runs a `POST` read-write, which is why the same reasoning reaches the opposite answer here. The meter therefore MOVED into a `BEFORE INSERT` trigger rather than being duplicated: two meters on one click would spend two units and silently halve the limit. A refusal is `PT429` — PostgREST's "return this HTTP status" escape, so a scripted caller gets a real 429 — with the seconds remaining in `hint`. **One deliberate difference from every other category, stated because it is a difference:** this counter does *not* count past its limit. A refused `INSERT` must raise, and a raise rolls back its own increment, so the count is read before the write and a refusal writes nothing at all; "10" here means "hit the ceiling", not "tried n times", and the crossing alert is filed by the last *accepted* request instead of by the first refused one. Q115.

**One mechanism, and the values live in the database.** `public.rate_limit_policies` is the only place a limit's value exists — seeded from this table verbatim and asserted against it row by row (`supabase/tests/rls_phase7_rate_limits.sql` § RV, which fails if a seventh category appears with no row here, or if a number drifts either way). Nothing in TypeScript holds a limit; `lib/security/rate-limit.ts` asks `public.consume_rate_limit()` and obeys the verdict, so the two halves cannot drift the way a mirrored constant could.

**Windows are FIXED, not sliding**, epoch-aligned by `private.rate_limit_window_start()`. The known cost is accepted and stated rather than hidden: **a burst straddling a boundary can reach 2× the limit across 2× the window** (60 discovery reads in the two seconds either side of a minute mark). A sliding window needs per-request timestamps or token-bucket state, which is more machinery than "basic counts only at MVP" warrants.

**Counters keep counting past the limit** — a refused request increments too. The count therefore measures *pressure* rather than permitted traffic (4,000 in a 30-limit window says something a clamped 31 hides), and the alert-at-crossing write depends on the refusing request's own increment committing, which is why `private.record_rate_limit_event()` returns a verdict rather than raising: a `RAISE` would roll back the refusal's count and its own alert row.

**FAIL CLOSED.** A counter write that errors refuses the request, in the app (`lib/security/rate-limit.ts`) and in the auth hook alike — the same direction every other gate in this codebase fails. The metered categories are retryable conveniences, so a false refusal costs a retry, while failing open turns any limiter outage into exactly the unmetered state this section exists to close. A refusal is 429-shaped in the app (`components/list/rate-limit-notice.tsx`, carrying the real remainder) and a distinguishable SQLSTATE at the database — never a silent empty result.

**THE NAMED RESIDUAL: the direct PostgREST path is not metered (Q107).** `GET /rest/v1/network_directory`, issued with the anon key and a session JWT, never enters the Next.js app and therefore never reaches the limiter. This is a measured constraint, not an oversight: **PostgREST executes every GET in a READ-ONLY transaction** (probed on this stack 2026-09-09 — a volatile function reached via `GET /rest/v1/rpc/…` fails with SQLSTATE 25006 "cannot execute INSERT in a read-only transaction", while the identical POST succeeds), and a rate limiter must WRITE, because the increment *is* the mechanism. So no policy term, view or pre-request hook evaluated inside a PostgREST GET can meter that path. The two DB-side shapes that could are both worse than the exposure: replacing the directory views with a POST RPC rebuilds the search path that Q86 forbids and the N2 `pg_depend` lock exists to prevent, and an autonomous-transaction hack (dblink, one extra connection per request) turns the mitigation into a connection-exhaustion DoS. **Recommended closure at Phase 10:** deny the direct-REST path for the two directory views outright via a server-held header checked in `pgrst.db_pre_request` — a DENY needs no write, so the read-only transaction does not block it. Until then the exposure is what Task 3 measured: on a 20k-profile corpus, `display_name` search is a Seq Scan at 44–86ms whose cost is **O(published profiles platform-wide)**, not O(tenant), because RLS's membership `exists` prevents the `ILIKE` from becoming an Index Cond. Also in § 10.

**Incident alerts read these counters.** Three trigger conditions write a platform-scoped `public.incident_alerts` row, superuser-read, shown on `/super/health`: a rate-limit crossing in any category (exactly once per window), repeated failed logins on one account (the login hook's own crossing), and a malware-scan quarantine hit (`private.document_quarantine_alert()`, which deliberately records the document id and never the filename — user-entered content does not belong on a platform surface). `notified_at` is the email seam: null means undelivered, and Task 6's Brevo sender stamps it with no schema change — **which needs a privilege, not only a column**: `service_role` holds `select` on the table and `update` on `notified_at` **and on no other column** (`20260909070000`). It had neither at first, because `BYPASSRLS` bypasses policies and not table privileges, so the seam had no access path at all. The operator's half is unchanged and the split is the point: a browser session may resolve and may not stamp, the sender may stamp and may not resolve. **The sender is wired (Phase 7 Task 6):** `lib/email/incident-alerts.ts` runs as `service_role` through `lib/supabase/service.ts`, reads `where notified_at is null` (bounded at 200), sends **one digest** through the one Brevo helper, and stamps **only the ids that digest carried, only after `ok:true`** — a failed send stamps nothing and the rows stay re-sendable; a sent-but-unstamped digest is logged and re-sent next run (a duplicate email is the honest failure, a silent stamp over an unsent row the dishonest one). Its entry point is `POST /api/incident-alerts/deliver`, a sessionless route behind `INCIDENT_ALERT_DELIVERY_SECRET` (constant-time compare; **404 when unset or wrong**, so an unconfigured deployment has no endpoint rather than an open one). **Nothing in the repo calls it on a schedule** — an external cron must, and that decision is Q118; see § 12. **An alert's `organisation_id` is never caller-supplied**: `public.consume_rate_limit()` accepts one only for organisation-scoped budgets and only after verifying membership (`20260909050000`), because a user-scoped category that passed a caller's organisation through let any authenticated account make the operator's alert feed name an innocent workspace. A user-scoped crossing therefore carries no workspace at all, and `/super/health` says so in words rather than rendering a blank. **But membership is not permission, and the guarantee is exactly that narrow (Q116).** The organisation branch gates on `private.is_active_member()`, and the RPC is granted to `authenticated` and callable straight over PostgREST — so any active member of a workspace, a Read Only one holding neither `manage_network_connections` nor any export right included, can `POST /rest/v1/rpc/consume_rate_limit` against **their own** organisation ten times, deny that workspace connection requests (or exports) for the rest of the hour, and file a `rate_limit_tripped` alert naming their own workspace. That is **in-tenant, not a tenant crossing** — what the check stops is a *stranger*, which is the property finding I1 was about — and it is pre-existing rather than introduced by that fix; it is disclosed here, in `lib/security/rate-limit.ts` and in the function's own comment (`20260909120000`) so the claim reads as "the caller belongs to the workspace" rather than "the caller is entitled to spend its budget". **Resolving and reopening an alert are audited** (`incident_alert.resolved` / `.reopened`, from an `AFTER UPDATE` trigger so a raw `PATCH` is covered too), because the reopen branch nulls `resolved_by` and the row alone could therefore not be the accountability record. SMS is out — no vendor chosen (Q111). Not a full alerting platform: a simple resolved flag, no dedup windows beyond the natural once-per-window crossing, no escalation or acknowledgement workflow.

**THE ALERT FEED IS FLOODABLE, and the mitigation is triage rather than volume (Q117).** Forging an alert's attribution is closed; *filing* alerts is not. One authenticated account can trip the two user-scoped budgets — `search` at 60/min and `network_discovery` at 30/min — roughly **twice a minute, ~2,880 a day**, and every one of those rows is `rate_limit_tripped`, open, and attributed to no workspace, so they are indistinguishable from each other. Two things bound the damage and neither stops the writes: the list is a **keyset pager**, so real alerts stay reachable instead of being pushed off a fixed ceiling, and it carries an **attribution filter** — "Attributed to a workspace" hides the entire flood in one click, because unattributed is exactly its shape — beside the type filter, the status filter and a summary search (the summary is the only place a crossing's *category* appears, since every category shares one alert type). The real fix is a per-subject dedup window (at most one `rate_limit_tripped` per subject/category per N windows); it is a schema decision that interacts with the exactly-once-per-window crossing write, and is queued rather than guessed.

**WHAT IS STILL UNMETERED, so the table is not read as covering everything.** Two write paths carry no budget. The **document-upload action** does real per-call work (byte read, magic-byte sniff, synchronous malware scan) and has no row here at all — its aggregate abuse IS bounded by the per-organisation storage quota (5GB Starter / 20GB Pro), which is not true of any other unmetered path, and picking a per-call number is a founder decision rather than an engineering default (Q113). Every other **CRM write** (creating a contact, an event, a note) is likewise unmetered: each is a small indexed insert inside one tenant, and no measurement suggests a budget is warranted — stated so that its absence reads as a decision rather than an oversight. And the direct PostgREST residual above applies to every `grant`ed table, not only the directory — **and to writes as well as reads, which an earlier version of this paragraph got wrong in the comfortable direction**. A session JWT can *read* any table its policies permit, and *write* any table its policies permit, without passing the app. That is what made the connection-request budget bypassable when it lived only in a server action (above), and it is why the answer there was a database trigger rather than a documented residual: for a **write** the database can meter, because PostgREST runs a `POST` in a read-write transaction. The unmetered-GET residual stands only where a *read* is the thing being counted. The directory is singled out among reads because it is the one whose unit cost is O(platform) rather than O(tenant).

**No `SECURITY DEFINER` search function was built to work around any of this** (Q86's standing constraint — a definer function on the network boundary is the shape that leaks). The limiter is the mitigation; the search path is unchanged.

## 6. File security

The pipeline is built as of Phase 4 Task 5 (`lib/crm/documents.ts` + `lib/security/*` + `app/(app)/[orgSlug]/documents/[documentId]/download/route.ts` + `20260902030000`/`20260902031000`) — upload, authorised signed-URL download, and soft-delete, each audited. The principles below, and how each is enforced as-built:

- **Private bucket, client-fenced.** The `documents` bucket is `public = false` (the primary control — no anonymous public URL exists), and `storage.objects` carries a **RESTRICTIVE deny-all policy** for `authenticated`/`anon` on the `documents` bucket (`20260902030000`). The browser is **never** handed a Storage grant.
- **Server-mediated I/O (Q53).** Every byte in and out goes through a Server Action / Route Handler running the **service-role** Storage client (`lib/supabase/storage.ts`) after the caller has been authorised. The upload action gates on `authoriseOrg(…, 'manage_documents')`, and the database's INSERT policy re-checks the same key — hiding the button is not the control, the refused write is.
- **Malware-scan every upload at MVP.** Behind the `MalwareScanner` interface (`lib/security/malware-scan.ts`). A local **EICAR stub** flags the standard test file so quarantine is fully exercisable on the local stack; a flagged file lands `scan_status = 'quarantined'` and **no signed URL is ever issued for it** (Task 5). The scan is synchronous at MVP (a real SaaS would move it to a webhook — a documented seam). **The real engine is not chosen yet:** `clamav`/SaaS adapters are unconfigured stubs that throw, selected by `MALWARE_SCANNER` (default `stub`); which engine and at what cost is **Q42**, a founder decision. **What cannot be exercised locally is a real antivirus verdict** — the stub proves the pipeline, not detection. See § 10.
- **A strict allowlist by content sniff, not MIME/extension.** `sniffAndAllow` (`lib/security/file-allowlist.ts`) reads the leading **magic bytes** and stores the *sniffed* MIME — a PNG renamed `.pdf` is stored as `image/png`, an `.exe` renamed `.pdf` is rejected. The accepted set is PDF, PNG, JPEG, WebP, GIF, plain text, CSV and the three modern OOXML documents (docx/xlsx/pptx); **macro-enabled OOXML (.docm/.xlsm/.pptm) and executables are rejected** — the OOXML zip family is inspected for a `vbaProject.bin` part or a `macroEnabled` content type and refused. The bucket's `allowed_mime_types` is belt-and-braces only; the client's declared Content-Type is untrusted.
- **Sanitised filenames, opaque keys.** `sanitiseFilename` produces a **display-only** name (path stripped, control chars and leading dots removed, length-capped); it never touches the storage key. The key is `buildStorageKey(orgId, documentId)` = `{org}/{doc}` — no filename, no user input — and the DB CHECK `documents_storage_key_shape` makes "inside my own tenant's prefix" a database invariant, so even a bug in the key builder is a 23514, not a cross-tenant file.
- **Every file action is logged.** Upload, download and soft-delete each write an audit row through `public.audit_document_action` (`20260902031000`) — the client-callable thin RPC over `private.log_audit_event` (which stays granted to no client role). A clean upload records `document_uploaded`, a malware hit `document_quarantined`, a download `document_downloaded` (written **before** the signed URL is issued — no audit, no URL), a soft-delete `document_deleted`. Identifiers only (org, document id): no filename, no bytes, because `audit_events` is superuser-readable. See § 7.
- **The feedback screenshot rides the same pipeline, on a second bucket (Phase 7 Task 6).** `feedback-screenshots` is `public = false`, 5 MiB, images only, with the same four **RESTRICTIVE** deny-all client fences (`20260911000000`); bytes go in through `submitFeedbackAction` (service-role Storage client, after `sniffAndAllow` reads the bytes as PNG/JPEG/WebP/GIF — a PDF is refused, a screenshot is an image), are scanned synchronously by the same `getScanner()`, and land on the row as a terminal verdict under an opaque `feedback/{id}` key pinned by CHECK. A quarantined screenshot is stored, never served, and files an `upload_quarantined` alert by trigger with the feedback id and never the message. **A session writer cannot DECLARE a screenshot** (fix round 1, `20260911020000`): the five screenshot columns are in the client INSERT grant because the app writes them after uploading, so on the raw PostgREST path a caller could name `feedback/<own id>` with a `clean` (or `quarantined`) verdict and no bytes; the trigger now requires the object to exist in `storage.objects` for the bucket, or 42501 — so "the row says there is a screenshot" means "the server put bytes there, sniffed and scanned". Bytes come out through one route, `/super/feedback/[id]/screenshot`, which checks the object exists, then audits, then signs — § 4 and § 7.
- **The framework body cap sits above both promises (Phase 7 Task 6 cleanup round, N5).** Both uploads travel as a Server Action body, which Next caps at `serverActions.bodySizeLimit` — **default 1 MB** — *before* the action runs, as a framework 413 and a generic client error. Measured: a 4.9 MiB screenshot behind "up to 5 MiB" and a 2 MB PDF behind "25 MiB" both died there, unseen by every gate because every upload fixture was a few hundred bytes. The cap is now **26 MiB** (`lib/security/upload-limits.ts`, read by `next.config.ts`): the largest promise (documents, 25 MiB) plus headroom for the multipart framing, deliberately above rather than equal to the promise so an upload just over it reaches the action and the *app's* "larger than the N MiB limit" sentence is the refusal the user reads (`feedback.spec.ts` drives a 6 MiB screenshot to it). Above 26 MiB the framework still answers first — a band no screen in the product accepts. Fails closed: nothing over the cap reaches storage. `tests/unit/security/upload-limits.test.ts` holds the cap to both promises so a raised promise cannot silently outgrow it again.
- **The download gate.** `issueDownloadUrl` loads the document **through RLS** (a cross-tenant id or a soft-deleted row returns nothing → 404, no existence leak), refuses anything but `scan_status = 'clean'` (→ 409, the quarantine gate), audits, and only then mints a **60-second** signed URL. The route redirects to it. A `pending`/`quarantined`/`error` document never yields a URL. Soft-delete marks `deleted_at` and audits; the **bytes are deliberately not hard-deleted** (soft-delete discipline — a retention/GC job that purges bytes for rows past retention is a Phase 8 follow-up). A **scan-status transition guard** (`before update` trigger) makes a terminal verdict immutable, so a stray PATCH cannot un-quarantine a file — defence in depth behind the fact that only the server sets `scan_status`.

## 7. Audit logging

- Every high-value action records: actor, org, timestamp, action, target, correlation ID, before/after values.
- Append-only from the application. Superuser access audits itself. Passwords, tokens and keys are never logged.
- Retention: hot/queryable for 30 days, archived (cold storage) for up to 1 year total, then purged. Deletion/alteration of audit records outside that lifecycle is restricted to a narrowly controlled platform security process.

### CRM writes: what is audited today, and what is not (Phase 2, fix round 1)

**Audited in the database, by trigger, so a direct PostgREST call cannot avoid it:** the two hard `DELETE` paths Phase 2 opened (`contact_companies`, `custom_field_values`) and every `merges` insert (`20260828141000`). A trigger rather than application code, for the same reason the `updated_at` trigger exists: `grant … to authenticated` plus the anon key that ships in the browser makes `DELETE /rest/v1/contact_companies?id=eq…` reachable without touching the Next.js app, so an application-side audit records only the deletions someone remembered to route through it.

**Every CRM `INSERT` and `UPDATE` is audited too, since Phase 7 Task 6b (`20260912000000`).** This paragraph used to say "not audited yet" and route the work to Task 6b (Q94); it shipped. The same trigger shape, on all eleven mutable Phase 2 tables (`companies`, `contacts`, `contact_companies`, `agencies`, `artists`, `artist_representations`, `artist_fee_history`, `venues`, `venue_rooms`, `custom_field_definitions`, `custom_field_values` — `merges` is append-only and its one `INSERT` was already audited), `AFTER INSERT OR UPDATE FOR EACH ROW`, so a raw `PATCH /rest/v1/contacts` is covered exactly as the form is. Four actions per table — `<target>.created`, `.updated`, `.soft_deleted`, `.restored` — with the last two distinguished at the trigger from a `deleted_at` transition so a soft-delete is never buried as "updated"; `soft_deleted`, not `deleted`, because `contact_company.deleted` and `custom_field_value.deleted` already mean a hard delete. Forty names, all in the viewer's catalogue (`lib/admin/audit-actions.ts`, offered by the Action filter as a `<datalist>`) and bound to the live `pg_trigger` arguments by `tests/integration/admin/audit-actions-match-db.test.ts`.

**The diff design — what an UPDATE row carries without breaking the no-content rule above.** `after.changed` is the sorted list of every column whose value changed (`updated_at` excluded, since the `BEFORE` trigger moves it on every write); `before.values`/`after.values` carry old and new **only for a per-table allowlist of structural columns** — ownership/assignment ids, foreign keys, booleans, dates, `deleted_at`, and `CHECK`-constrained closed vocabularies (`companies.type`, `entity_type`, `field_type`, `currency`). For everything else — name, email, phone, title, location, website, socials, tags, genres, country, city, notes, address, capacity, technical info, role, territory, fee amounts, custom-field keys, labels, options and values — the row says "`notes` changed" and never what it changed to. The allowlist is **one function**, `private.audit_crm_value_columns(target_type)`, and it is the only thing the trigger reads to decide what it may copy, so a column added later is name-only until someone edits that function and justifies the addition in the migration header — fail-safe, where a denylist would have leaked the new column on the day it shipped. An `INSERT` row carries the same projection over the whole new row. A no-op `UPDATE` (nothing but `updated_at` moved) writes no row. **The property is measured, not asserted**, from three positions per table: `supabase/tests/rls_phase7_crm_audit.sql` § CU (a member's session in psql), `tests/integration/security/crm-audit-no-content-leak.test.ts` (a real member's supabase-js client over PostgREST), and `tests/e2e/audit-log.spec.ts` (the real edit form, then the founder's screen) — each writes a sentinel into a content column and searches the audit row's whole `before`/`after` for it.

**The exemption, and why it is `auth.uid()`.** The trigger writes nothing when `auth.uid()` is null: migrations, seeds, DBA repair and the cascades they start (`ON DELETE SET NULL` on `owner_user_id` fires an UPDATE with no session). No client path is exempt — `service_role` holds no grant on any of the eleven tables (measured, § CX3). It is `auth.uid()` and **not** `row_security_active()`, because the latter is false inside every `SECURITY DEFINER` function and would have silently skipped any write made from inside one (Task 5 I4's lesson, re-proved here: § CX2 writes from inside a definer and reads the row back).

**Bulk paths share one thread.** The four multi-row RPCs — `merge_records`, `set_contact_primary_company`, `set_artist_primary_representation`, `set_custom_field_values` — would each have sprayed one freshly-minted `correlation_id` per touched row. `20260912001000` reuses Task 3's threading mechanism through a **second GUC** (`app.crm_bulk_correlation_id`, consulted by `log_audit_event()` as a fourth coalesce step) rather than the lifecycle marker, because that marker is also the second term of `organisations_update_platform_lifecycle` and a member must not be able to set a policy term. Each RPC's body was **moved** to `private.<name>_unthreaded` and wrapped under its original name, so the only routable merge is the threaded one (the runner's HTTP block asserts the moved bodies are 404). A merge now reads as one thread: the winner's `contact.updated` naming `phone` and not its value, the loser's `contact.soft_deleted`, every repointed link's `contact_company.updated` (old and new `contact_id`), every carried or swept custom-field value, `records.merged` and `records.merged.fields` — measured in § CB.

**Volume and retention — Q94's second question, answered with numbers.** One row per `INSERT`, one per effective `UPDATE`. A `contact.updated` row with one changed column is **221 bytes of heap** (5,000 rows = 1,080 kB, measured on the 5,000-row bulk fixture) — but **472 bytes** once `audit_events`' six indexes are counted, and **472 is the figure any volume projection must use**. This paragraph previously quoted the heap number alone, as "216 bytes", which understates real storage by more than half. Worked at the honest rate: 100 workspaces averaging 200 audited CRM writes a day is 20,000 rows/day ≈ 9.4 MB/day — roughly **283 MB across the 30-day hot window** and **3.4 GB by the 1-year archive boundary** the purge job enforces. On the golden path, each Phase 2 step (create contact, company, link, artist, venue, room) writes exactly one `.created` row beside its record, a primary-company change writes two `contact_company.updated` rows on one thread, and the Phase 3/4 steps (event, lineup, task) write none — see the paragraph below. **Measured end to end rather than asserted:** a walk of eight inserts, an edit, a primary-company change, a soft-delete, a restore, an edit-while-deleted and a restore-with-rename produced **16 audit rows across 15 distinct correlation ids**, with no sentinel leak anywhere in them. Note what that thread count means in practice: only the RPC's pair shares an id, so "one correlation id per user action" describes a multi-row RPC and **not** an ordinary form save, which is several requests and therefore several threads. The audit table therefore grows at roughly the rate of the tenant tables it watches — an audit row is smaller than the record it describes — and CLAUDE.md's 30-day hot / 1-year archive lifecycle bounds it; the purge job that implements that lifecycle is the same Phase 8 machinery every other retention clock in this product waits on (Q120). **No per-table opt-out is built**, deliberately: it would be speculative infrastructure for a volume nobody has measured as a problem, and an opt-out is a hole in the audit trail with a switch on it. If a tenant's write rate ever makes this material, the shape to add is Task 3's — threading plus a summary row, or suppression as one more branch in `log_audit_event()` — not a switch per table. **Performance:** a row-level trigger on every write costs **~0.36 ms per row** (5,000-row bulk `UPDATE` as a member: 2,177 ms with the trigger, 395 ms without — the difference is `log_audit_event()`'s definer call, the jsonb diff, the organisation lookup and six index inserts). Per request that is invisible; for a bulk operation it is the price of the evidence, and stated. (An independent re-measurement on a contended machine gave 3,407 ms against 552 ms — 0.57 ms/row — so treat 0.36 ms as the floor rather than a constant.) **The whole-suite `pnpm test` before/after that the same requirement asks for is NOT measurable on this machine, and no number is offered for it:** identical code ran **178 s and 1,908 s** on two runs, and the pre-task tree ran **406 s**, the spread tracking free memory (3+ GB versus under 1 GB, with a second Supabase stack up) rather than anything in this change. The isolated per-row cost above is the honest answer.

**The viewer's action filter gained `audit_events_action_created_at_id_desc_idx` `(action, created_at desc, id desc)` — and it is a bet on scale, not a win this product's row count can demonstrate.** This paragraph previously claimed the filtered keyset page was "an Index Only Scan, 28 buffers / 0.06 ms, against 288 buffers / 1.99 ms without it". **That claim is withdrawn: it was wrong twice over.** An Index Only Scan is structurally impossible for this query — `fetchAuditLogPage` selects `before`/`after`, and a `(action, created_at, id)` index cannot cover a jsonb column — so the quoted plan cannot have come from the viewer's query at any size. And re-measured with `EXPLAIN (ANALYZE, BUFFERS)` on that function's real select list after `ANALYZE`, the numbers do not reproduce. What is actually true, measured: **at 5,000 rows the planner never chooses it.** A common action (99% of rows) walks `audit_events_created_at_idx` backward with a filter (4 buffers, 0.12 ms); a rare one (0.5%) uses `audit_events_action_idx` and sorts (27 buffers, 0.24 ms); dropping the composite index changes neither plan nor buffer count. **At 200,000 rows the planner does choose it, for a rare action** — 52 buffers and 0.15 ms, against 1,028 buffers and 1.21 ms for the `action`-index-plus-top-N-sort it falls back to without it: ~20× the buffers and ~8× the time, and that gap widens with the table. For a *common* action it is chosen at neither size, because walking the `created_at` index and discarding non-matches reaches a page of 25 almost immediately when nearly every row matches. **The index is kept on exactly that evidence** — its write cost is already counted in the 472 bytes above, and it pays for itself on rare-action queries once the table is large, which is the direction CRM write auditing takes it. Today it is a projection, and this section now says so.

**What is NOT covered, named rather than implied:** the Phase 3–6 tables (`events`, `event_lineup`, `event_status_changes`, `tasks`, `meetings`, `notes`, `documents`, the four `*_links` tables, `financial_entries`, and the network tables beyond their existing publish/visibility audit) carry no `INSERT`/`UPDATE` audit. Q94 and `FOLLOW-UPS.md` scoped Task 6b to "the twelve" Phase 2 tables; extending the same trigger and allowlist function to the later phases is one branch in `audit_crm_value_columns()` plus two triggers per table, and is queued as **Q122** rather than done silently.

**The audit payload is an allowlist of identifiers, never user-entered content.** `private.audit_crm_payload()` projects each audited row down to its identifiers and structure and drops `custom_field_values.value` and `merges.field_resolution`. `audit_events` is readable by exactly one principal — the platform superuser — and `CLAUDE.md` § Superuser dashboard keeps tenant record content off that surface, describing the in-app feedback screenshot as *the one* deliberate exception. Dumping deleted rows into `before` would have quietly created a second one. **The cost:** this audit answers "who deleted what, when" and does **not** support restore-from-audit. If restore is wanted it needs a founder decision about superuser access to tenant content, or a tenant-scoped undo table rather than `audit_events`.

**Sessionless writers emit no audit row.** The trigger returns early when `auth.uid()` is null, because `private.log_audit_event()` raises `28000` on a null actor and an unconditional trigger would abort `DELETE FROM organisations` (which cascades into both audited tables with no session). What that excludes is migrations, seeds, DBA repair and the cascades they start — not any client path, since `service_role` holds no grant on these tables.

### Impersonation: every transition AND every page reached (Phase 7 Task 2)

**Six audited actions on `target_type = 'impersonation_session'`:** `impersonation.requested`, `.accepted`, `.declined`, `.started`, `.page_viewed`, and `.ended`/`.expired` (`20260908020000`). The first five transitions are written **inside the same `SECURITY DEFINER` RPC that performs the transition**, in one transaction — so a state change that is not audited is a state change that did not commit. That is stronger than either of the two shapes above and is warranted: this is the only path by which a non-member reads a tenant.

**The session id is the correlation key.** `private.log_audit_event()` mints a fresh `correlation_id` per call unless given one; every row this flow writes passes the session id, so `select * from audit_events where correlation_id = <session id> order by created_at` is the complete, ordered story of one impersonation — request, consent, start, every route reached, end — with no join. `target_id` carries the same value deliberately: `correlation_id` is the thread, `target_id` is what the row is *about*, and the audit log viewer filters on different ones of those. Every row also carries `organisation_id` = the **target** organisation, so an impersonation surfaces to anyone filtering that tenant's events, and `actor_user_id` = the **real** actor — `log_audit_event` forces `auth.uid()` and accepts no override, so the accept row names the admin who consented and the rest name the superuser. Nothing in this feature borrows an identity.

**Page access is audited APP-SIDE, at the resolver, and the placement is the decision.** `public.audit_impersonated_page_view(org, route)` is guarded by **the grant itself** (`private.impersonated_organisations`), so a caller with no live session mints no row; the app calls it from `lib/admin/impersonation-session.ts`'s `resolveImpersonationForOrg()`, which `getCurrentOrg()` reaches on **every** org-scoped page. A layout-level audit would have recorded the first page of a session and none of the rest, because an `[orgSlug]` layout does not re-run on a client-side navigation between two routes that share it. **It fails closed**: a refused audit write returns "not impersonating", and the route renders the ordinary tenant-isolation 404 — there is no path that serves an impersonated page without a matching audit row. **It over-records rather than under-records**, and that is the deliberate opposite of the audit-log viewer's own prefetch decision (Task 1): a Next.js prefetch of an org route renders the layout and therefore lands a `page_viewed` row for a page nobody read. A trail listing a route nobody opened is noise; one missing a route somebody did open is a hole in the product's only deep-access path.

**ROUTE ONLY, NEVER CONTENT.** The RPC's signature has no parameter that could carry a record name, a search term or a result count, and the app strips the query string before calling (`auditableRoute()` in `lib/admin/impersonation-contract.ts`) — `?q=` is where a list page's search term lives, and a search term is a fragment of what the tenant's records say. A path **segment**'s record id is deliberately kept: knowing which record support opened is the entire point. `rls_phase7_impersonation.sql` § IA6 asserts the `after` payload's key set is exactly `{route}`.

### Organisation lifecycle: one summary row per transition, and a general threading mechanism (Phase 7 Task 3)

**Three audited actions on `target_type = 'organisation'`:** `organisation.suspended`, `organisation.deleted`, `organisation.reinstated` (`20260908030000`). Each is written by `private.log_organisation_lifecycle_event()` in the same transaction as the transition, so a state change that is not audited is a state change that did not commit — the impersonation shape above, for the same reason: these are the operator's most consequential actions on a customer.

**The `after` payload is a SUMMARY, and it is counts, never rows.** New state, `lifecycle_changed_at`, `retention_expires_at`, the operator's verbatim reason, the subscription period end that governs network presence, and COUNTS of what the transition touched (active members, published profiles). No name, no email, no record id — so this stays inside `CLAUDE.md` § Superuser dashboard's "aggregate metadata, never record content", the same discipline `rls_phase7_impersonation.sql` § IA asserts for the impersonation rows. `rls_phase7_lifecycle.sql` LA5 asserts it directly.

**THE CASCADE-AUDIT ANSWER, and it is deliberately general.** `FOLLOW-UPS.md` had an open question about the organisation-delete path emitting one audit row per cascaded child, each with its own `correlation_id`, because `private.log_audit_event()` mints a fresh one per call. That function now resolves the id in **three** steps rather than two: an explicit `p_correlation_id` wins, then the thread `private.begin_lifecycle_transition()` declares, then — unchanged — a fresh uuid. **An operation declares itself once and every audit row written anywhere inside it, by any trigger including one added years later, joins one thread with no call site edited.** `private.end_lifecycle_transition()` closes it, and the pairing is not optional: an `is_local` GUC stands to the end of the *transaction* whatever `SET` clauses the call stack carries. **Suppression was considered and rejected** — it discards evidence to save space, in the table whose purpose is evidence, and unrecoverably. **Phase 8's hard purge and the DSR erasure must reuse this** rather than inventing their own: declare once, do the work, write one summary row.

**The operator's reason is CUSTOMER-VISIBLE, deliberately and with a test.** `organisations.lifecycle_reason` sits on a table every active member can read (`organisations_select_member`); RLS filters rows and not columns, and Postgres column privileges are per-ROLE — the superuser and the customer are both `authenticated` — so hiding it from the workspace while showing it to the operator is not an available arrangement. Task 3's self-review found the first cut disclosing it through PostgREST while the banner hid it, which is the worst of the three options; the product now renders it on the banner and both operator forms warn in the field hint. `rls_phase7_lifecycle.sql` LA5a/LA5b assert a member reads it and a foreign Owner does not. **An operator must not put anything in that field the customer may not read**; an internal-only note would be a second column no member-facing query projects (DECISIONS-QUEUE Q103).

**The marker is also a security control, not only an audit one.** `private.lifecycle_transition_in_progress()` is the second term of `organisations_update_platform_lifecycle`, so a raw `PATCH /rest/v1/organisations` from the superuser's own browser — who is on the allowlist, at aal2, and can read the row — matches nothing. That is what makes "every lifecycle transition is audited with a reason" structurally true rather than conventionally true. It is not a boundary against a hostile superuser; nothing in this schema is.

### In-app feedback: three audited actions on `target_type = 'feedback'` (Phase 7 Task 6)

**`feedback.submitted`** and **`feedback.status_changed`** are written by triggers (`private.audit_feedback_submission()`, `private.audit_feedback_status_change()`, `20260911000000`) — the CRM hard-delete reasoning, because `public.feedback` carries a client INSERT grant and a client UPDATE(status) grant, so a raw PostgREST `POST`/`PATCH` is a real path no call site could cover. The submission payload is category, role, route and the screenshot verdict, **never the message**: `audit_events` is the superuser's log and the message already has its own, deliberately separate, surface. **`feedback.screenshot_viewed`** is app-side through a guarded RPC (`public.audit_feedback_screenshot_view()`), written by `lib/feedback/screenshot.ts` **before** the signed URL is minted — the document-download order, for the document-download reason: the bytes have no second path (the bucket is client-fenced), so the application is the only reader and the audit is a precondition of the URL, not a side effect. Since fix round 1 the route also checks the object **exists** (storage-js `exists()`, service-role) *before* the audit call, so a row whose bytes are missing answers 404 with no audit row rather than an audit row followed by a 500 — an audit row must record a view that could happen. Every row's actor is forced to `auth.uid()`; a sessionless writer (fixture, seed) audits nothing, the `audit_crm_row` rule. Measured: `rls_phase7_feedback.sql` § FI13/FI14, § FU2, § FA5; the browser path in `tests/e2e/feedback.spec.ts` reads the `screenshot_viewed` count out of Postgres around the real link.

### Document actions: audited APP-SIDE, and why that differs from CRM writes (Phase 4 Task 5)

**Three new audited actions, on `target_type = 'document'`:** `document_uploaded`, `document_downloaded`, `document_deleted`, plus `document_quarantined` for a malware hit (`20260902031000`). Each is written by the application — the upload/delete Server Actions and the download Route Handler — through `public.audit_document_action`, a **thin client-callable RPC** over `private.log_audit_event`. The private writer stays granted to no client role; the public wrapper is the only reachable surface and it is **guarded**: the caller must hold `view_crm` in the org **and** the document must really belong to that org, so a forged RPC call cannot mint audit rows for orgs or documents the caller has no relationship with (the actor is always forced to `auth.uid()`).

**APP-SIDE, not a trigger — the opposite decision from the CRM hard-delete audit above, on purpose.** The CRM audit is a trigger because `grant … to authenticated` plus the browser's anon key makes a raw `DELETE /rest/v1/contact_companies?id=eq…` reachable **without the app**, so the database is the only chokepoint. A document's **bytes have no such second path**: `storage.objects` for the `documents` bucket is deny-all fenced to every client role (`20260902030000`), and the only principal that can read or write a `documents` object is `service_role`, on the server. There is no PostgREST-reachable "download this file" endpoint to bypass — an upload is a Server Action and a download is a Route Handler, and both run the audit before they touch Storage. So for documents the **application is the only path in and out**, and an app-side audit is sufficient and correct. The **download audit in particular is written before the signed URL is issued** (`issueDownloadUrl`), so a logged access is a precondition of a served file, not a side effect of it. The metadata row *is* client-reachable, but a metadata write is not the audited event — the sensitive action is the movement of bytes, which is server-only; the scan-status transition guard is the metadata-side defence in depth.

## 8. Data retention and residency

- Soft-delete operational records rather than hard deletion, subject to retention policy.
- Working defaults (pending legal sign-off — see `CLAUDE.md` § Legal and regulatory compliance): **7 years** for financial records, **2 years** for inactive-account data (also applied to in-app feedback submissions — see `CLAUDE.md` § In-app feedback), **30 days hot / 1 year archived** for audit logs.
- **Feedback retention is enforced at READ time (Phase 7 Task 6):** `feedback_select_platform` carries `created_at >= private.feedback_retention_cutoff()` (now − 2 years), and the screenshot-view RPC re-tests the same cutoff, so an expired row is unreadable on every path — the app, a direct PostgREST GET, the signed-URL route — with nothing scheduled (the Q88 / Task 4 pattern). Measured: `rls_phase7_feedback.sql` FR6/FA7. **The rows and their screenshot bytes are not yet purged**; that joins the Phase 8 retention job Q110/Q52 already owe (Q120). A submitter's account erasure cascades to their feedback rows (`on delete cascade`, unlike `audit_events`), so a DSR does not wait on that job.
- GDPR data subject requests (export/erasure): **30-day** target, matching the ICO statutory maximum.
- **Data residency: UK/EU Supabase region only** — no US-region hosting for customer data.
- Currency: **GBP only at MVP**; schema (`financial_entries` etc.) stores a currency column and minor units so multi-currency UI can be added later without a migration.

**`supabase-audit-rls` is a live pentest tool. Rules for using it:**

1. **Never against production.** Local Supabase or a seeded staging project only.
2. **Anon key only** — never the service-role key; the point is to attack from the client's position.
3. It writes `.sb-pentest-context.json` and `.sb-pentest-audit.log` into the working directory. Both are gitignored: findings and keys never get committed.
4. Findings are triaged into this file's § 10 (Known risk areas), not left in the log.
5. It supplements the written RLS integration tests — it does not replace them. A policy is verified by a test that runs in CI, every time.

## 12. Incident response

Current stage (single founder, pre-launch): no formal on-call rotation yet.

- **Security contact:** the founder is the sole point of contact at this stage. *(TODO before launch: set up a dedicated security contact channel — see §13 — rather than a personal inbox.)*
- **Severity tiers:**
  - **Sev1** — active breach, confirmed data exposure, or a live exploit: response target **1 hour**.
  - **Sev2** — exploitable vulnerability, no evidence of exploitation: response target **24 hours**.
  - **Sev3** — low-risk finding, hardening opportunity: addressed **next sprint**.
- **Regulatory obligation:** notifiable UK GDPR breaches must be reported to the ICO without undue delay and, where feasible, within **72 hours** — this clock starts independent of the internal severity tiers above.
- A full written runbook (roles, communication plan, customer notification templates, post-incident review process) is still to be drafted — flag as open work before handling real customer data.
- **Basic trigger-based alerting ships at MVP** via the superuser dashboard, and since Phase 7 Task 5 it is built: three triggers write `public.incident_alerts` rows (rate-limit crossing, repeated failed logins, malware-scan quarantine) and `/super/health` is where they surface. This is not a full alerting/observability platform — just enough to catch the incidents in the severity table above before a customer reports them. **What is true after Phase 7 Task 6c, stated precisely:** the sender exists and is wired (`lib/email/incident-alerts.ts` → the one Brevo helper, § 5), it stamps `notified_at` only after a successful send, it is invoked by `POST /api/incident-alerts/deliver` behind a server-held bearer secret — **and the clock now exists.** Founder ruling Q118 put it in the database: `pg_cron` runs the job `incident-alert-delivery` **every 10 minutes**, calling `private.deliver_incident_alerts()` (`20260916000000`), which POSTs that route through `pg_net` with the bearer. **Where the bearer lives:** Supabase Vault (`vault.decrypted_secrets`, entries `incident_alert_delivery_url` and `incident_alert_delivery_secret`), created by hand once per environment and **never by a migration** — a GUC is readable from any session, a settings table is plaintext in every backup, and a bearer baked into `cron.job.command` is echoed in `pg_stat_activity` on every tick. **Local dev and CI have no cron in any meaningful sense:** the job is registered (so its schedule and command are testable) and the function returns before it builds a request whenever either Vault entry is missing, which is every environment this repository can reach. It does not guess a localhost URL and it does not present an empty bearer. **When a send fails** — Brevo down, the route down, the network down — the sender stamps nothing, the rows stay `notified_at is null`, and the next tick picks up the identical set; retry *is* the schedule, with no backoff, no dead-letter and no retry counter, and the alert stays visible on `/super/health` throughout. **Two overlapping runs can double-SEND one digest and cannot double-STAMP it** (the stamp matches `where notified_at is null`): the duplicate is accepted, and written into the migration header so nobody "fixes" it with a claim-before-send, which would mark rows delivered that nothing had emailed. **Overlap itself is made unreachable by bounding the route, not by arguing about timeouts** (fix round 1, M1): `20260916000000`'s header claimed a 10-second Brevo timeout ruled overlap out, which stopped being true the moment `20260916001000` added a sequential per-account lockout loop to the same route — at its first 100-account limit a degraded Brevo gave a ~1000-second worst case against a 600-second cadence, so a credential-stuffing spray could have produced duplicate account-holder notices. That loop is now capped at 30 accounts per tick with a 120-second wall-clock budget (worst case ~140 s), and `20260917000000` reissues the corrected `comment on function`. An advisory lock in `private.deliver_incident_alerts()` would not have helped: `net.http_post` is fire-and-forget, so the function returns — and releases anything it holds — before the route runs. Until `SUPPORT_CONTACT_EMAIL` / `BREVO_*` / `INCIDENT_ALERT_DELIVERY_SECRET` and the two Vault entries are set (§ 15), an alert is still a row and not an email — the difference is that the clock is no longer the missing piece. **SMS is not built at all** — no vendor is chosen (Q111) — so "email/SMS" above describes the intent. **A second, separate notification rides the same clock:** the per-account lockout email (§ 5, Q114), which is *not* folded into the operator's digest.

## 15. Pre-launch security checklist (config that does not ship itself)

`supabase/config.toml` governs the **local CLI stack only**. Nothing in this repo pushes it to a hosted Supabase project, so every value below must be set by hand in the hosted project's dashboard before launch, or the control it represents does not exist in the environment that matters:

- `jwt_expiry = 900` — bounds how long an already-issued access token keeps working after its underlying session has been invalidated server-side. Left at the 3600s default, that window is an hour.
- `[auth.sessions] timebox = "12h"` and `inactivity_timeout = "30m"` — these are what actually enforce the session limits in § 4; the app-side idle tracker is a proactive UX layer on top, not the enforcement.
- `[auth.mfa.totp] enroll_enabled` / `verify_enabled = true` — without these the MFA gate has nothing to enroll or challenge against.
- `minimum_password_length = 10` — must match `MIN_PASSWORD_LENGTH` in `lib/forms.ts`, or the app's validation is bypassable by calling GoTrue directly.
- **Email delivery (Phase 7 Task 6) — four environment values and one cron, none of which ships itself:** `BREVO_API_KEY` / `BREVO_SENDER_EMAIL` / `BREVO_SENDER_NAME` (`docs/email-setup.md` — domain authentication first, or mail lands in spam), `SUPPORT_CONTACT_EMAIL` (§ 13), and `INCIDENT_ALERT_DELIVERY_SECRET` (≥ 32 chars) **plus the two Supabase Vault entries the database's own clock reads** (Q118): `select vault.create_secret('https://<host>/api/incident-alerts/deliver', 'incident_alert_delivery_url', '…');` and `select vault.create_secret('<the same value as INCIDENT_ALERT_DELIVERY_SECRET>', 'incident_alert_delivery_secret', '…');`. The `pg_cron` job ships with the schema (`20260916000000`, every 10 minutes) and is a silent no-op until both entries exist — so a deploy that sets the environment variables and forgets the Vault entries has a scheduler that runs and delivers nothing. Verify with `select * from cron.job_run_details order by start_time desc limit 5;` and `select status_code from net._http_response order by created desc limit 5;`. With any of these missing the product degrades honestly — feedback is stored and shown "email not sent", alerts stay rows — but silently as far as the inbox is concerned. Verify after deploy by submitting one feedback and confirming the receipt arrives and the row on `/super/feedback` no longer reads "email not sent"; then `curl -X POST -H "Authorization: Bearer …" https://<host>/api/incident-alerts/deliver` and confirm a JSON `outcome`, never a 404. Sign Brevo's DPA before real personal data flows (`docs/sub-processors.md`). Every Brevo call carries a 10-second timeout (`BREVO_TIMEOUT_MS`, fix round 1 I2) and the feedback receipt runs after the submission's response through `next/server`'s `after()`, so a Brevo stall can neither hang a submission nor, via the retry it invited, duplicate the row. **Supabase Auth's own mail (sign-up, magic link, reset) is NOT relayed through Brevo today** — that is a hosted-project SMTP setting nothing in this repository configures (`docs/email-setup.md` § 3); until it is done, auth mail is Supabase's built-in sender and Brevo processes only the support contact's address and feedback receipts.
- **`[auth.hook.password_verification_attempt] enabled = true`, pointing at `pg-functions://postgres/public/hook_password_verification_attempt`** — this is the whole of § 5's per-account login limit. A hook that is not enabled in the hosted dashboard is a limit that does not exist, and it fails silently: sign-in keeps working, brute force is simply unmetered, and nothing in the app can tell. Verify after deploy by making six failed sign-ins against a test account and confirming the sixth is refused *and* that a `repeated_login_failures` row appears in `public.incident_alerts`.

### The platform superuser grant

`public.platform_admins` is the platform-superuser allowlist. It has RLS enabled with **zero policies and zero client grants**, so no client role — not even a leaked service-role key — can write to it. Rows are added by migration or DBA action only, and it seeds **empty** on purpose.

That is the correct shape for the table and a launch blocker for the product, because three separately-correct decisions compose into a dead end while it stays empty:

- `audit_events`' only SELECT policy is `has_platform_permission('view_audit_log')`. **With an empty allowlist the audit trail is write-only** — it is being recorded correctly and cannot be read by anyone, through any path the application offers.
- **Corrected 2026-09-08 (Phase 7 Task A) — the premise changed.** `organisation_subscriptions`' write policies are still superuser-only, but `create_organisation()` now writes a Starter row for every new organisation at birth (`20260908000000`), and every organisation that predates that migration was backfilled one — so an empty `platform_admins` no longer strands every organisation on Free. The dead end that remains is narrower: **no organisation can ever be moved off Starter** (upgraded to Pro, comped, or otherwise billing-overridden) with an empty allowlist, because `organisation_subscriptions_update_platform_billing` is the only write path and it is superuser-gated. Starter carries `crmWrites: true`, so this is a growth/upsell dead end, not a "every write in the product refuses" one — still worth fixing before launch, but not the same severity this row used to claim.
- The Platform-Superuser branch of the MFA gate and `public.is_platform_admin()` are dead code until a row exists.

`supabase/migrations/20260827210500_seed_platform_superuser.sql` grants it to the founder. Two things about it need checking after deploy, which is why it is on this list rather than assumed done:

1. **It looks the user up by email, and is a no-op if that account does not exist yet.** No Supabase auth user id existed when it was written, so it could not hardcode a UUID. If the migration is applied before the founder has signed up, the allowlist stays empty and the migration must be re-run afterwards. It is idempotent (`on conflict do nothing`), so re-running is safe.
2. **Verify the row actually landed**, rather than assuming the migration did it:
   ```sql
   select u.email from public.platform_admins pa join auth.users u on u.id = pa.user_id;
   ```
   An empty result means the product is in the dead-end state described above.

Granting or revoking further superusers is documented in that migration's header. Note that allowlist membership is necessary but **not sufficient**: per § 4 and `20260827210000_mfa_aal_permission_gate.sql`, every platform permission also requires an `aal2` session, so the founder must enrol TOTP before any superuser-gated policy will pass.

### Response security headers

Set in code, not config, so they ship with the app rather than needing a hosted-dashboard step — listed here so a launch review can confirm them rather than assume them. `lib/security/headers.ts` is the single definition; `next.config.ts` applies the static ones and `proxy.ts` applies the nonce-bearing CSP.

Two of them are **deliberately conditional on `NEXT_PUBLIC_SITE_URL` being `https:`**, and therefore are NOT present in local development:

- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
- `upgrade-insecure-requests` in the CSP

So confirm on the deployed environment, by reading actual response headers (`curl -sSI https://<host>/login`), that both appear. If `NEXT_PUBLIC_SITE_URL` is misconfigured to `http://` in production, the app will work and will silently ship without HSTS.
