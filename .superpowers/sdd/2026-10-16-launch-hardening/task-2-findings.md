# Task 2 findings: the OWASP pass (audit phase)

Written 2026-10-17 at branch `launch-hardening`, tip `34d6afd`, read-only.
No code, test, migration or config file was changed, and no database, server
or e2e run was made: the shared local stack was in use by Task 4. Every
finding is therefore evidenced from source, from the repository's own
existing assertions, or from the installed library code. Where a finding was
not reproduced, its row says so.

**The audit stopped early on F1 (Critical),** as the brief requires. Scope
covered before the stop, and what is left, are in `task-2-report.md`.

Severity rubric (the brief's): Critical = demonstrated or plausible tenant
breakout / private-network leak / auth bypass / data loss; High = a promised
control missing or bypassable; Medium = defence-in-depth gap on a control
otherwise enforced; Low = hygiene.

## Remaining audit scope (fix phase): no new finding

- **CRM Server Action bodies** (`lib/crm/*.ts`, `lib/network/*.ts`, `lib/consent`, `lib/dsr/actions.ts`, `lib/feedback/actions.ts`, `lib/org/*.ts`): every action resolves the workspace through `getCurrentOrg()` (RLS) and writes through the caller's RLS client with an explicit `.eq("organisation_id", org.id)` and `{ count: "exact" }`. A scripted check for `.update(`/`.delete(` without a tenant filter within 14 lines flagged 3 sites; all three carry it further down (`contacts.ts:423`, `custom-field-actions.ts:301`, `events.ts:493`). Redirect targets are `/${org.slug}/...` built from database values and ids, so always same-origin. The privileged clients reachable from actions: `lib/org/actions.ts` (Admin API, after the MFA and `has_permission` pre-checks; the abuse half is F9), `lib/crm/documents.ts` and `lib/feedback/actions.ts` (Storage, after an RLS row read; covered by the audit phase's file-path review).
- **Admin Server Actions** (`lib/admin/*.ts`, `lib/legal/admin-actions.ts`, `lib/dsr/admin-actions.ts`, `lib/feedback/admin-actions.ts`): every write is a `SECURITY DEFINER` RPC (or an RLS update) through the caller's own client, gated in the database on a platform permission at aal2. Every step-up gate is app-layer (G13); all of them call `checkStepUp()`, which Task 6's census enumerates.
- **Runners** (`app/api/{exports,erasure,retention}/run/route.ts`, `app/api/incident-alerts/deliver/route.ts`; `lib/{export,erasure,retention}/runner.ts`): each route requires its own >= 32-character bearer secret, compares it in constant time and answers 404 whether it is wrong or unset; no route takes an argument that chooses work except retention's `dry: true`. The export runner reads rows as the requester through `export_read_page`, includes document bytes only for `scan_status = 'clean'` (others are listed as withheld) and reads keys pinned by `documents_storage_key_shape`; screenshot keys are derived (`feedback/{id}`). The erasure and retention runners take their manifests from definer RPCs and only remove what those return.
