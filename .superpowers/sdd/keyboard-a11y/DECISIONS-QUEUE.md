# Keyboard-a11y pass — decisions queue for the founder

Side pass on branch `keyboard-a11y` (stacked on loading-skeletons → sidebar-nav), not a numbered phase, so entries are labelled `KA-n` per the loading-skeletons precedent. All proceeding on the stated default; each reversible. Scope was founder-fixed (baseline keyboard operability everywhere + a global Ctrl/Cmd-K palette; explicitly NO j/k list navigation, NO shortcuts cheat-sheet, NO power layer) — nothing below expands it.

- **KA-1 — pending buttons are now `aria-disabled`, not `disabled`.** `components/ui/button.tsx`: the native `disabled` attribute on a just-activated submit blurs it to `<body>`, dropping a keyboard user's position once per form, product-wide. Pending now keeps the element focusable (`aria-disabled` + `aria-busy` + a click guard that blocks re-activation, implicit form submission included) so focus survives the round trip. Permanently blocked controls (tier/role gates, with `aria-describedby` explanations and e2e attribute-stripping tests) keep the native attribute — nothing about server-side enforcement changes. **Default taken: aria-disabled pending ships.** Veto path: restore `disabled={disabled || pending}` and drop the guard — one file.

- **KA-2 — the palette searches eight entities, not all of them.** Contacts, companies, artists, venues, agencies, events, tasks, meetings — each through its OWN list spec via `fetchListPage` (no new query path, five rows per entity, min two characters, 250ms debounce). Excluded deliberately: **notes** (search column is the body; surfacing body fragments of `company`-visibility notes in a global palette is a product call not yet made — RLS would enforce visibility correctly, this is about surprise, not leakage), **documents** (no detail page to land on), **network discovery** (has its own surface and its own deferred rate-limit posture, Q86/Q87 — the palette does not open a second cross-tenant search path beside it). Flag if notes-in-palette is wanted; it is an additive entry in `lib/palette/entities.ts` plus the product decision.

- **KA-3 — palette search cost: up to 16 parallel bounded queries per settled keystroke.** Eight page reads + eight counts (the count is `fetchListPage`'s built-in and feeds the "All N matching…" escape rows). Each is the same query the entity's list page runs at page-size 5; the debounce and two-character minimum bound the rate. No rate limiter is added — search reads carry none anywhere else either (the deferred Q86 limiter is discovery-specific). If palette search cost ever matters, a `skipCount` option on `fetchListPage` is the first lever.

- **KA-4 — Escape does not unpin a pinned rail.** The queued Esc-to-collapse courtesy applies to hover/focus expansion only; a pinned rail ignores Escape because the pin is an explicit, persisted preference whose dismissal belongs to the pin button. Flag if Escape-unpins is preferred.

- **KA-5 — inline confirmations gained focus management, not dialog semantics.** `delete-restore`/`request-actions`/`link-picker` keep the recorded no-modal design (nothing inert, no aria-modal, no trap); they now move focus to the revealed question (never a button a repeated Enter could fire), return it to the trigger on cancel, and cancel on Escape. The palette, by contrast, IS a modal dialog (scrim, aria-modal, one tab stop) because it overlays unrelated content. Two different shapes on purpose.

- **KA-6 — focus loss on server-revalidation swaps is a recorded residual, not fixed here.** Buttons that succeed and then unmount or swap via revalidation (link-panel "Make primary", representation-panel Remove↔Restore/primary swaps, room-panel Close↔Reopen, profile-editor "Hide now", custom-field Remove→Restore section moves, per-row Unlink/Detach on success) still drop focus to `<body>` after a SUCCESSFUL action — KA-1 fixed the during-flight loss; the after-success loss needs a per-surface "where should focus go once this row is gone" answer that deserves design rather than a blanket jump to #main. Logged in FOLLOW-UPS.md with the recommended shape.
