## What was built

### `supabase/migrations/20261030003000_integrations_in_the_privacy_lifecycle.sql`

The migration number is 20261030003000, not the brief's 20261030002000, because Task 2's fix round took that one. Every existing function here was rebuilt from its live `pg_get_functiondef`. The file was generated by a script that copies each live definition byte for byte and asserts each insertion matched exactly once.

1. **`private.integration_connections_guard()`** gets two changes:
   - On a revoked row, `created_by` and `revoked_by` may now move to the Q130 tombstone as well as to NULL. `owner_user_id` gets no such exemption.
   - **A new rail the brief did not name.** It covers a live person-scoped row whose `owner_user_id` is set to NULL by the foreign key's ON DELETE SET NULL, which happens when an account is deleted outside `erase_account()` (the Auth admin API or Studio). That write now revokes the row in place: the Vault secret is deleted (by id and by name), the status becomes `revoked`, and the revoke is audited `integration.revoked` with reason `account_deleted` and the tombstone as actor.
   - I measured why it is needed. The FK's SET NULL fires before any AFTER trigger on the cascaded membership. So without this rail, an out-of-band delete still turned the person's mailbox into a live workspace-scoped connection, orphaned its secret, and failed with 23505 beside a live connection to the same provider.
2. **`private.revoke_integration_row(p_connection_id, p_actor, p_reason) returns boolean`** (new). It locks the row and is idempotent: a missing or already-revoked row returns false and writes no audit. Otherwise it:
   - deletes the Vault secret by id AND by the name `integration:<id>`;
   - marks the row revoked with `revoked_by = p_actor`;
   - audits `integration.revoked` with payload `{provider, owner_scoped}`, plus `reason` when one is given. It goes through `log_audit_event()` when `p_actor` is the session's person; otherwise it inserts directly, with `p_actor` or the tombstone as actor.
   - EXECUTE is revoked from every client role.
3. **`public.revoke_integration()`** is rebuilt from its live (Task 2 fix-round) definition. Its authorisation checks are unchanged. Everything after them is now one call, `revoke_integration_row(v_c.id, v_uid, null)`, so the RPC's payload is still exactly `{provider, owner_scoped}`. The idempotence now lives in the primitive.
4. **`private.integration_connections_follow_membership()`** plus an AFTER DELETE or UPDATE OF status, user_id, organisation_id trigger on `organisation_memberships`. A membership ends when:
   - the row is deleted;
   - its status moves to `revoked`;
   - or it is moved to another person or workspace.

   When one ends, every live person-scoped connection that person owns in that workspace is revoked through (2), with reason `membership_ended` and actor = the remover if they are a real account, otherwise the tombstone. Workspace-scoped connections the person created are untouched.
5. **`private.erase_account()` step 5c**, placed before step 6, so well before the auth.users delete:
   - each connection with `owner_user_id = person` is revoked through (2), with the tombstone as actor and reason `account_erased`;
   - its runs are deleted, then the row;
   - `created_by` and `revoked_by = person` are re-pointed to the tombstone on the remaining rows. Step 7's generic re-point covers only NO ACTION keys, and these two are SET NULL.

   The summary gains four counts.
6. **`private.erase_organisation()` step 5c.** It deletes the workspace's Vault secrets (by `token_secret_id` and by name), then the connections (their runs cascade), before the org delete. The summary gains `integration_secrets` and `integration_connections`.
7. **`private.export_catalogue()`.** The three interim excused rows are replaced:
   - **workspace `integration_connections`:** requester_rls, scope `organisation_id`, with an explicit 12-column projection that names `token_secret_id` OUT;
   - **workspace `integration_sync_runs`:** requester_rls, scope `organisation_id`;
   - **account `integration_connections`:** requester_rls, scope `owner_user_id`, same projection.
8. **`private.fkless_identifier_columns()`.** The `token_secret_id` row keeps its classification (`other` / `not_a_person`). Its interim note is replaced by the final one, which names the step 5c handling.
9. **Retention:**
   - `retention_periods()` gains two classes: `integration_sync_run` (90 days, from `finished_at`) and `integration_connection_revoked` (2 years, from `revoked_at`);
   - the two interim `cascades` rows in `retention_subjects()` become `swept` under those classes;
   - a new `private.sweep_integration_records(p_dry, p_limit)` sweeps finished runs, then revoked connections (deleting any Vault secret still filed under such a connection's name);
   - `retention_sweep_body()` runs the new sweep in its own subtransaction (refusal key `integrations`);
   - `retention_clock_columns()` classifies `integration_connections.revoked_at` and `integration_sync_runs.finished_at` as `clock`. The walk derives exactly those two candidates (IN3).
10. A self-check DO block at the end: the catalogue is sound, both tables are exported, `token_secret_id` is projected out, both subjects are swept, both classes resolve, and no provider is live.

`private.audit_payload_person_columns()` needed no change. It is derived from the CRM audit triggers, and neither integration table carries one. The integration payloads hold no person column; IE7 and IE8 measure the payload scan.

## Concerns

- **Out-of-band account deletes.** A revoked ownerless row is left behind, and an Owner or Admin reads its metadata as a workspace connection (provider, scopes, dates). It is revoked and holds no token. Deleting the row from a BEFORE UPDATE trigger during an RI action is not safe, so I did not.
- **A sync run stuck `running` is on no clock.** The `integration_sync_run` class keys on `finished_at`. A crashed connector's run would live until its connection or workspace goes. Worth a reaper when a live connector exists.
- **The leakage suite is not re-runnable on one database**, as described above. This is pre-existing, not from this task.
- **The legal v8 is unreviewed.** Like every page, it carries no counsel-review marker.
- No founder question was raised.
